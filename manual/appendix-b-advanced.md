# 附录 B　进阶玩法

正文按「在界面上点」写；这一本附录收那些界面之外、偶尔用得上的东西。

## 处理器类名

[第 6 章](06-add-streamer-and-push.md)的通知开关在界面上点就行，用不到类名。
要用自定义插件提供的处理器、或直接手写配置文件 `datasource.json` 时，才需要
下表的全文类名——文件里要写全限定名，照抄即可：

| 处理器全限定名 | 界面上的名字 | 触发时机 | 可用占位符 |
|---|---|---|---|
| `org.frostnova.nova.bilibili.handler.BilibiliLiveOnPushHandler` | 开播通知 | 开播 | `{uname}` `{title}` `{cover}` `{url}` `{at}` `{next}` `{at=all}` |
| `org.frostnova.nova.bilibili.handler.BilibiliLiveOffPushHandler` | 下播通知 | 下播 | `{uname}` `{time}` `{url}` `{next}` `{at=all}` |
| `org.frostnova.nova.report.handler.BilibiliDynamicPushHandler` | 动态通知 | 动态更新 | `{uname}` `{action}` `{url}` `{picture}` `{at}` `{next}` `{at=all}` |
| `org.frostnova.nova.report.handler.BilibiliLiveReportPushHandler` | 直播报告 | 下播 | 只发图，旧文字模板不再生效；画图失败时发文字版报告 |
| `org.frostnova.nova.report.handler.BilibiliOfflineRewardDigestPushHandler` | 下播打赏播报 | 不在播时有人上舰或送礼够格，攒完一阵（见[第 6 章](06-add-streamer-and-push.md#下播打赏播报)） | `{uname}` `{list}` `{url}` `{picture}` `{next}` `{at=all}` |

推送页的运营周报可以「发送上一周的报告」，直播报告可以「发送上一份直播报告」。两者都只发往当前通道，确认后真实发送，不影响后续定时周报或下播推送。

**前缀不止一种**：动态通知、直播报告与下播打赏播报住在报告插件里（`org.frostnova.nova.report.handler.`），
其余两个在哔哩哔哩插件里。`{next}` 的意思是「从这里分成两条消息」——在界面的模板
编辑器里不用写它，多建一张卡就是多一条（见第 6 章）。

> [!NOTE] 从 starbot 时代升上来的老配置不用急着改：旧全名（`com.starlwr.bot.`
> 开头的）仍被认，日志里会提醒一句「这个处理器现在叫什么、建议改过来」。
> 其中动态通知与直播报告原先住在哔哩哔哩插件包下，照上表改过来即可，
> 改之前推送照常。下播打赏播报没有 starbot 时代的名字，但它的旧全名
> （`org.frostnova.nova.bilibili.handler.` 开头的那一份）同样仍被认。

## 每场留下的事件流水

每场直播的明细落在数据目录的 `details/<平台>-<uid>-<开播时刻>/` 下。其中
`events.jsonl` 逐条记下礼物、盲盒、上舰、关注、PK 的开打与结算，一行一条 JSON，
以时刻 `at`（毫秒）与类型 `t` 打头，其余是短键：

| `t` | 含义 | 字段 |
|---|---|---|
| `gift` | 付费礼物 | `uid` 观众、`un` 昵称、`gid` 礼物 id、`gn` 礼物名、`n` 数量、`val` 到手价值、`pay` 实扣、`bag` 是否背包 |
| `box` | 盲盒 | `uid`、`un`、`bn` 投入盒名、`bp` 实扣、`gid`／`gn`／`n` 开出物、`val` 开出面值、`pft` 盈亏 |
| `guard` | 上舰 | `uid`、`un`、`lv` 等级（舰长 3／提督 2／总督 1）、`ot` 开通（1）／续费（2）／未知（-1）、`n` 数量、`u` 单位、`days` 陪伴天数、`val` 价值、`pay` 实扣 |
| `follow` | 关注 | `uid`、`un` |
| `pk_open` | PK 开打 | `pk` 场次号、`tp` PK 类型、`nc` 参加家数、`ps`／`pe` 计划开始与结束（秒）、`op` 对手一串（`r` 房间号、`u` 主播 uid） |
| `pk_settle` | PK 结算 | `pk`、`tp`、`nc`、`er` 提前结算（1／0）、`en` 实际结束（秒）、`mv` 本房票数、`mr` 本房名次、`rs` 本房结果（1 胜／0 负／2 平）、`op` 对手一串（`r`、`u`、`v` 票数、`k` 名次） |

几点读法：

- 上舰的 `ot` 记的是稳定码而不是显示字：1 开通、2 续费、-1 解析不出，旧档里没有这一字段的行按未知读
- 上舰的 `pay` 是实扣；平台未给实付时按 `val` 记
- PK 的票数只是这场的拉票结果，**不算收入**，所以它叫 `mv`／`v` 而不是 `val`／`pay`
- 弹幕与醒目留言的原文在同目录的 `danmu.jsonl`；进场与点赞只计数，不进事件流水
- `danmu.jsonl` 每行记录 `at`（发送时刻，毫秒）、`uid`、`uname`、`text`、`type`；补录行另有 `recovered: true`。`type=SUPER_CHAT` 的行还记录可选的 `val`（这条醒目留言的金额，单位元，与本场 `super_chat_value` 同口径，直接取事件金额）。其他类型不写 `val`；旧行缺少 `val` 表示金额未知，读取不会改写，也不会补成 0 元
- 进场次数另按分钟记成时序，与其它曲线一起归档在每场的 `detail.json` 里
- 一场最多留 50 万行流水，到了会在日志里说明一声，本场后面的不再收录

同一数据目录下的 `image-cache/` 存着直播报告用过的礼物图标和大航海标志，程序重启后不用重新下载。三十天没再被读到的会自动删掉。整个目录删掉也行：正在出的报告会重新下载；回看以前的场次不联网，缺的那几张画成占位。

`excluded-viewers.json` 也在同一数据目录，供 MCP 等外部只读查询标记智能助手「不分析」的观众：`excludedUids` 是去重后升序排列的观众 uid 数组，`updatedAt` 是本次名单写入时的 Unix 毫秒时间戳，`version` 是格式版本号（当前为 `1`）；启动时按当前设置生成，控制台保存名单后立即更新，相同名单不重写，清空后仍保留文件并写成空数组，不含昵称或其他设置。

旁边的 `report-render-cache/` 存着直播报告推送时的成品原图，每张通常几百 KB 到数 MB，随报告内容和版式而变；每位主播只留最近一场的各套外观，三十天没再被读到会自动删掉。删掉目录后仍能「发送上一份直播报告」，但会从明细重画，封面和头像用占位图，也不画粉丝增减。

## 让事件去触发一个脚本

开播时启动录播、上舰时写一行记录、被切流时给自己发条提醒——这类内置功能覆盖不到的用法，
可以挂一个外部程序：

```yaml
novabot:
  core:
    exec:
      enabled: true          # ⚠️ 默认关闭
      timeout: 30            # 单条命令最长执行时间，单位：秒
      max-concurrent: 4      # 同时执行的命令数上限，超出的直接丢弃
      rules:
        - event: LiveOnEvent
          command:
            - /opt/scripts/record.sh
            - "{room_id}"
            - "--name={uname}"
```

`enabled` 与 `timeout` 也能在设置页「外部程序触发」「外部程序触发 · 超时」里改，保存后下一个事件就按新值处理，不用重启；
`rules` 与 `max-concurrent` 改了仍要重启。

`event` 填事件类名，简名或全限定名都行，**沿继承链匹配**——填 `LiveOnEvent`
就能同时命中各平台的具体开播事件。可用占位符：
`{event}` `{platform}` `{uid}` `{uname}` `{room_id}` `{timestamp}` `{json}`。

> [!WARNING] `command` 是参数数组，不是一整行命令。第一项是可执行文件，填写固定的程序名或路径，
> 不使用占位符；其余各项各自是一个独立参数。想用管道、重定向之类的 shell 特性，
> 请自己写一个脚本文件再在这里填它的路径。占位符替换后的内容无论含空格、引号还是换行，
> 都仍是原来那**一个参数**。

用解释器运行脚本时，脚本路径也填写固定值。未列出的占位符按原文保留，空参数也保留，`null` 项跳过。

第一项之外，`{event}` `{platform}` `{uid}` `{room_id}` `{timestamp}` `{json}` 可以单独成一项，
也可以和固定文字写在同一项里。程序的选项名写固定文字；`{uname}` 用作选项值时，
目标程序支持哪一种写法，就选哪一种：

- 长选项合写成一个参数：`--选项名=` 后接占位符，例如 `"--name={uname}"`。
- 短选项合写成一个参数：`-` 加选项字母后直接接占位符，例如 `"-n{uname}"`，
  用于目标程序允许把值紧跟在短选项后面的情形。
- 程序支持 `--` 时，先列固定选项，再单列一个固定的 `--`，后面填写事件参数。
- 脚本自行读取事件内容时，在这条规则上加 `event-environment: true`，从环境变量
  `NOVABOT_EVENT_JSON` 读取事件 JSON，`command` 可以全部写固定值。

`{uname}` 写在固定文字之后（例如 `"./{uname}"`）也照常替换。

例如，目标程序支持 `--` 时可以这样写：

```yaml
        - event: LiveOnEvent
          command:
            - /opt/bin/recorder
            - --quiet
            - --
            - "{room_id}"
            - "{uname}"
```

固定的 `--` 之前，某一项替换后若以 `-` 开头（单个 `-` 除外），这一项开头须是上面两种固定的
选项写法，否则跳过本次命令，日志里写明是哪一条规则；同一条规则每次运行只记一次。固定参数沿用原文。`--` 是否有分隔作用由
目标程序决定，请按目标程序的用法填写，程序不会自动添加它。

`event-environment` 默认是 `false`，打开后仅对这次启动的子进程设置 `NOVABOT_EVENT_JSON`，
子进程的其他环境变量照常继承。它与 `{json}` 使用同一份格式：超过 8000 个字符或无法
生成时传空字符串。标准输入仍为空。JSON 中的事件字段可按自己的脚本需要读取；
不要把读取出的内容再拼成一整行命令。

启动时会逐条检查规则；运行中有规则因参数写法被跳过时，也会补入提醒。同一条规则本次运行只提醒一次。需要调整的规则，日志里会有一句提示，管理员打开控制台时，
页面顶部也会列出是哪几条（按 `novabot.core.exec.rules[序号]` 指明，序号从 0 数起）。按上面的写法修改这几条的
`command`；第一项使用了占位符的，改填固定程序或脚本路径。修改后重启，提醒随之不再出现。
控制台按实际生效的规则更新清单，只有管理员能看到；保存在配置文件里、尚未重启的改动不改变当前清单。
没有提示且照常执行的规则不用改。

超时只结束命令本身，它拉起的其他程序（若有）会接着跑——要长时间运行的程序（例如录播），
请在脚本里把它放到后台、让脚本自己尽快退出，例如在脚本里写这样一行：

```bash
nohup 录播程序 ... >/dev/null 2>&1 &
```

并发超过上限的那次**直接丢弃并记日志**，而不是排队——
等到十分钟后才执行的「开播启动录播」没有任何意义。

## 把事件推给别的程序

把直播间事件按「事件输出协议」实时推给**本机的其他程序**，用于自建面板、独立统计
这类内置功能覆盖不到的场景。它只输出，不接受任何指令：

```yaml
novabot:
  core:
    event-stream:
      enabled: true               # 默认关闭
      path: /nova/events
      buffer-size: 2000
      allowed-origins: []          # 浏览器面板填写页面来源，如 https://panel.example
```

打开后地址是 `ws://127.0.0.1:<端口>/nova/events`，与配置界面共用端口。客户端先发送只读口令，
成功后服务端发一条 `hello`（带会话标识与能力集），随后是实时事件；每条事件有一个会话内严格递增的 `seq`，
断线重连时用 `resume` 就能把缺的那段补回来。协议的每一帧长什么样、时限是多少，见
[事件源协议](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/protocol.md)。

> [!NOTE] 这一段以前写在 `starbot.bilibili` 下。事件输出由核心提供，与接的是哪个平台无关，
> 配置也就跟着挪到了 `novabot.core`。5.4 起旧键不再识别；写在旧位置的设置启动时日志会用
> WARN 说明没被读取、该挪到哪，照着挪完重启。

> [!WARNING] **只接受来自本机回环地址的连接，且这一点与 `server.address` 无关。**
> 即使你为了对外提供推送接口把监听地址改成了 `0.0.0.0`，事件流也只认本机。
> 需要从其他机器读取请自行建立 SSH 隧道（`ssh -L 7828:127.0.0.1:7827 你的服务器`）。
> 直接暴露到公网风险自负——这条流里有观众的昵称、uid 与消费金额。

几条口径上的提醒，连上后 `hello` 里的 `notes` 字段也会重复一遍：

- **点赞未聚合**，每次点赞单独一条、`count` 恒为 1
- **`live_state` 没有中途接入的快照**，只在开播、下播、标题变更时下发
- **`source_state` 的 `disconnected` 只在主播被移出数据源时下发**，还在监听列表里时一律是 `reconnecting`
- **房管标志只有弹幕消息带**，其余消息恒为 `false`，含义是「这条消息没说」而不是「不是房管」
- **`emoji` 只在「整条弹幕就是一张表情图」时非空**，判断「这条带表情」要读 `inlineEmojis`
- 每条事件附带平台原始报文（`rawJson`），**字段随平台改版而变，不要当契约用**

**一条连接承载全部房间**，每条信封上都有 `room`，下游必须按它过滤——不滤的后果不只是
「消息多了」：曾有下游把别的主播的礼物一起算进了当前主播的本场累计，主播看到一个错的数字
而界面上没有任何提示。`seq` 也是整条连接共用的，所以过滤时**只能丢消息，不能丢序号**：
按 `room` 筛掉几条之后，本房间的下一条 `seq` 自然不连续，把它当跳号处理就会凭空报出一次
不存在的断档。判断有没有真丢包，要看**整条连接**的 `seq` 连不连续。

缓冲是全部房间共用的一条流。房间多或弹幕密时要把 `buffer-size` 调大，否则客户端重连时会
被告知补不上而必须清空重来；每条约数 KB，调大前先掂量内存。

**事件输出始终要求只读口令，客户端要先开口。** 设置页上没有关掉它的开关；配置文件里留着的 `require-token` 照样能启动，填写 `false` 也按 `true` 运行。口令只在连接建立后的第一帧出示：

```json
{"kind":"auth","token":"<口令>"}
```

认证成功之前服务端什么都不发，连 `hello` 也不发——所以别等 `hello` 再发口令，会一直等
到 10 秒后被断开。口令在控制台「连接」页的「外部面板」卡上签发（只读，见[第 12 章](12-settings.md#其他几项)），**明文只在签发那一刻显示一次**；
签发时要填「令牌名称」，否则日后无法单独吊销。吊销会立即断开用该口令认证的所有已有连接，
其他口令的连接不受影响。口令只填在首帧里；握手不要填写 `Authorization`、
`nova.token.` 开头的子协议或口令查询参数（HTTP 400），普通子协议及其他查询参数照常使用。
完整的参数名约定见[事件源协议 §1](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/protocol.md#1-传输与端点)。

**新接入的面板建议改用访问令牌。** 管理员在控制台「访问令牌」页（见下文「让脚本或别的程序调用 NovaBot」）签发时勾上
「读取事件流」（`events:read`，仅管理员），把这把 `nvb_` 开头的令牌照样填进首帧的 `token`，其余步骤不变。
它能设有效期，也能和调 `/nova/api/v1/` 的程序共用一把；在控制台吊销它、停用它所属的账号或把账号降为成员时，
用它连着的面板当场断开，到期后十几秒内断开。没勾这一项的令牌连不上事件流，收到的回应与填错口令一样。
旧的只读口令照常能用，已经接好的面板不用改。事件流仍只接受本机连接：「访问令牌」页「从别的机器访问」里的开关
只管 `/nova/api/v1/`，打开哪一组都不会让别的机器连上事件流，跨机读取照旧用 SSH 隧道。
同一台机器上 1 分钟内出示访问令牌失败满 10 次后，这一分钟里再用访问令牌连会被当作「暂忙」断开，面板照常重连即可；只读口令不受影响。

浏览器面板还需把页面来源填入 `novabot.core.event-stream.allowed-origins`，修改后重启。
填写页面地址的协议、主机及可选端口，如 `https://panel.example` 或 `http://localhost:7830`，
不带路径、末尾斜线或通配符；默认空表。列表以外的页面来源返回 HTTP 403。
页面来源按浏览器实际值填写，默认端口 80/443 会自动去掉；IPv6 主机须保留方括号，域名使用 ASCII 写法（国际化域名先转为 Punycode），不加末尾斜线。
保存时会检查写法；启动时若配置格式不合，事件输出暂停，程序和控制台照常启动，可在设置中修改后重启。
不带 `Origin` 的本机程序照常连接，并在首帧出示只读口令。

### 事件输出的连接额度与等待时间

以下键位于 `novabot.core.event-stream`，省略时使用默认值；填写正整数，修改后重启。
填写零或负数时使用默认值，日志会提示调整方法；填写文字、空值或超出整数范围的数时程序无法启动，日志会指出是哪个键，改正后重启。

| 配置键 | 默认值 | 用法 |
|---|---|---|
| `max-connections` | `256` | 全部连接的总额度，包含握手、等待首帧与收尾中的连接 |
| `max-pending-connections` | `128` | 等待首帧的连接额度，包含握手中的连接；首帧通过后归还 |
| `max-connections-per-source` | `128` | 每个对端地址的连接额度；同一代理或隧道转入的连接共用额度 |
| `max-concurrent-handshakes` | `64` | 同时进行的 WebSocket 握手数 |
| `handshake-timeout-ms` | `10000` | 从握手开始到连接建立的等待毫秒数 |
| `io-timeout-ms` | `10000` | 内置服务端单次写入与关闭等待的毫秒数 |

达到额度时，新的握手返回 HTTP `503`，并带 `Retry-After: 5`，客户端至少等待 5 秒后再试。
已建立的连接继续工作；日志会指出可调整的配置键，按实际面板数量增大对应额度后重启即可。
连接收尾完成后归还额度；握手等待到期的连接不进入事件流，客户端稍后重新连接。
写入等待到期时结束该连接，客户端按原有 `sessionId`、`seq` 约定重新连接与回补。
每条连接可接收全部房间，无需按房间另建连接。现有配置可直接使用，无需增加部署步骤。

## 让脚本或别的程序调用 NovaBot

自己写的脚本、别的程序要读 NovaBot 里的东西，用**访问令牌**调 `/nova/api/v1/` 下的接口。
令牌挂在你登录控制台的那个账号名下，管理员和成员都能给自己签。这个前缀下有一个自查接口
`/nova/api/v1/me`（问「我是谁、能看见哪些主播」）、管理员用来代发消息的「推送」一组（见下文「发一条消息」），
插件提供的接口也挂在它下面（例如外发箱）。
地址、返回格式、错误代码的完整约定见
[程序接口约定](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/api.md)。

### 签发一把令牌

1. 点侧栏底部的「访问令牌」（手机上先点右上角「我的」）。
2. 填「令牌名称」，例如「备份脚本」，日后好认出是哪一把；名字可以重复。
3. 勾选范围（插件登记了才有可勾的项；一项不勾的令牌只能调 `/me`），选有效期：不过期、30 天、90 天或 365 天。
   标着「仅管理员」的范围管的是整个实例，成员那里是灰的、勾不了。
4. 点「签发令牌」，再点「复制」。**明文只显示这一次**，离开这一页就看不到了；
   NovaBot 只存它的摘要，取不回明文，丢了只能吊销再签一把。

令牌形如 `nvb_` 后接 43 个字符。程序在请求头里带上它：

```bash
curl -H "Authorization: Bearer nvb_..." http://127.0.0.1:7827/nova/api/v1/me
```

只认这个请求头。写在地址栏参数里、或者只带着控制台的登录状态，一律回 401；
反过来，访问令牌也登不进控制台。每个账号最多同时有 20 把有效令牌，满了先吊销不用的再签。

令牌的权限一直跟着账号走：

- 成员的令牌只看得见管理员分给这个成员的那几位主播；管理员改了分配，下一个请求就按新的算。
- 管理员被改成成员，这个账号以前签的令牌也按成员算，带「仅管理员」范围的那些接口调不动了。

### 发一条消息

管理员签令牌时勾上「发送推送消息」（`push:send`，仅管理员），程序就能请 NovaBot 代发消息，
经哪个机器人发都行（QQ、QQ 官方机器人、外发，看这台机器装了哪些）。先问一下能往哪儿发：

```bash
curl -H "Authorization: Bearer nvb_..." http://127.0.0.1:7827/nova/api/v1/push/platforms
```

回包里每个去向有 `id`（下面要填的 `platform`）、显示名、能发往的目标种类（`FRIEND` 好友、`GROUP` 群）。
然后发一条：

```bash
curl -X POST http://127.0.0.1:7827/nova/api/v1/push/messages \
  -H "Authorization: Bearer nvb_..." -H "Content-Type: application/json" \
  -d '{"platform":"qq-onebot","targetType":"GROUP","target":"123456789","content":"今晚八点开播"}'
```

- 号码建议写成字符串。`content` 的写法与推送模板相同（`{at=all}`、图片占位符照常用），但一次只发一条，不能写 `{next}`。
  `{image_url=…}` 的地址默认不许指向本机、内网和链路本地地址，要从内网取图时在设置页「消息图片 · 允许的内网网段」里放行；
  机器上配了系统代理或用了假地址解析时，按域名的判断不起作用，直接写内网地址的照样拦得住，见[第 12 章](12-settings.md#改完怎么保存)。
- 回 `"delivery":"SENT"` 是发出了；回 `"delivery":"UNKNOWN"` 是交出去了没等到明确结果，**可能已经发出，别让脚本自动重发**。
  写错字段、去向不存在、去向被停用、对方拒收都回错误，说明里写着是哪一种，这些情形下消息都没发出。
- 与旧推送接口一样，**不受「全局推送开关」和静音时段管**，首页按了「暂停全部推送」也照发；去向被停用时不发。
- 同一把令牌每分钟最多 600 条，超了回 429，等 `Retry-After` 写的秒数再发。
- 每一次发送都记在日志页的时间线上（「推送」那一类）：哪个账号的哪把令牌、发往哪个机器人的群还是好友，号码只露头尾两位，不记正文。

旧的推送接口 `POST /onebot/send`（每个机器人一把写在配置文件里的口令）照常能用，已经接好的程序不用改；
新接入的建议用这一组：令牌按账号签、随时能吊销，每一次发送都查得到是谁发的。
错误代码与回包的完整写法见[程序接口约定「推送」](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/api.md#推送)。

### 令牌什么时候失效

- **过期**：到了签发时选的有效期。
- **吊销**：在这一页点了「吊销」。
- **账号停用或删除**：名下的令牌**一并吊销**。吊销不能撤回，账号重新启用后旧令牌仍然作废，要用得重新签发。
  停用成员时的确认框里也写着这一句。
- **成员此刻登录不了控制台**（统一登录关着、或控制台的登录口令被撤掉）：成员名下的令牌**暂不可用**，
  调接口收到 401；成员能登录了，下一个请求起自动恢复，不用重签。管理员的令牌不受影响。
  列表里这种令牌的状态写「暂不可用」，下面一行写着原因。

前三种过后只能重新签发；最后一种等它自己恢复。

### 吊销

还是那一页，列表里每一把有效（或暂不可用）的令牌后面有「吊销」，已过期、已吊销的那些没有。
成员只看得到、只吊销得了自己的；管理员看得到所有账号的令牌，也都能吊销。
吊销后，用它的程序从下一个请求起就会收到 401。
签发与吊销都会记进控制台操作记录（数据目录下的 `console-audit/`，见[第 13 章](13-upgrade-and-backup.md#控制台操作记录)），记的是令牌编号，不是令牌本身；
停用、删除账号时一并吊销的，在那一条记录里只记吊销了几把。

**控制台总开关关着时，既签不了新令牌，也吊销不了旧令牌**（这一页在控制台里）。这时某把令牌泄露了：
先在 `application.yml` 里把那一组从「对任何地址开放的接口组」（`novabot.core.config-ui.api-any-source-groups`）里去掉，
本机以外拿到令牌的那一方从下一个请求起就进不来；
再把控制台打开，到这一页吊销它，或停用它所属的账号。

### 从另一台机器连

默认只有 NovaBot 所在的那台机器上的程序调得了这个前缀：直接连本机回环、不经反向代理的才算本机。
别的机器要调哪一组，就在「从别的机器访问」里打开哪一组。设置页的「允许访问的来源 IP」只管控制台能从哪里打开，不影响接口。
「访问令牌」页最下面的「从别的机器访问」（只有管理员看得到）按这台机器此刻的端口、监听地址与内网地址，
写好了本机、内网、公网、SSH 隧道各该连哪个地址，以及现在通不通、还差哪几步。四种连法：

- **同一台机器上**：`http://127.0.0.1:7827/nova/api/v1/`，什么都不用改——前提是「监听地址」是默认的 `127.0.0.1`
  或 `0.0.0.0`。监听地址设成了某一个具体地址（例如 `192.168.1.20`）时，`127.0.0.1` 上没人听，
  同一台机器上也要连 `http://192.168.1.20:7827/nova/api/v1/`；这样连进来的在 NovaBot 看来是 `192.168.1.20`、
  不是本机，没打开要调的那一组就会收到 403。
- **内网别的机器**：`http://<这台机器的内网地址>:7827/nova/api/v1/`。要先做两件事：
  1. 设置页的「监听地址」默认是 `127.0.0.1`，只有本机连得上。改成 `0.0.0.0`（或这台机器的内网地址），保存后重启；
  2. 在「从别的机器访问」里打开它要调的那一组。只开那一组，别的组仍只有本机调得了，控制台也不受影响。
- **公网**：经反向代理的加密地址，例如 `https://<你的域名>/nova/api/v1/`。反向代理要按
  [附录 C 的样板](appendix-c-security-and-resources.md#让别的机器经反向代理调程序接口)转发 `/nova/api/v1/` 并带上转发头；
  **转发了也不等于放通**：经反向代理进来的在 NovaBot 看来都不是本机，调不调得了要看「从别的机器访问」里那组开没开。
  控制台的公网地址不一定调得通接口：反向代理只转发了 `/config` 的，接口地址照样 404。
  **不要没有反向代理就把端口直接放到公网**：那样令牌会明文经过网络。
- **SSH 隧道**：不改任何设置的办法。在调用方那台机器上开

  ```bash
  ssh -N -L 7827:127.0.0.1:7827 用户名@服务器地址
  ```

  然后照常请求 `http://127.0.0.1:7827/nova/api/v1/...`。在 NovaBot 看来它是本机来访，开关不用动。
  监听地址设成了某一个具体地址时同上：隧道另一头要连那个地址（`ssh -N -L 7827:192.168.1.20:7827 …`），
  NovaBot 看到的来访者也是那个地址、不是本机，要打开要调的那一组。「从别的机器访问」里会按实际的监听地址写好。

「从别的机器访问」里每组接口一个开关「允许从任何地址访问（仍须访问令牌）」。打开时会先问一句：
任何能连到这台机器这个端口的人都能尝试调用这组接口，全靠令牌把关。保存即生效，不用重启；
关掉之后，本机以外的来访者从下一个请求起就回到 403。开放只免去「只许本机」这一道，令牌、范围、
「仅管理员」的范围和无效令牌限速一样不少；至少开了一组时，自查接口 `/me` 也随之开放。
开关存在设置项「程序接口 · 对任何地址开放的接口组」（`novabot.core.config-ui.api-any-source-groups`）里，
设置页上也能改。没打开时，本机以外的来访者会收到 403，说明里写着「这个请求不是从本机直接发来的……
这组接口没有对本机以外的地址开放；管理员可在控制台「访问令牌」页的「从别的机器访问」里打开」。
这些开关只管 `/nova/api/v1/` 下的接口：事件输出 `/nova/events` 不在里面，仍只接受本机连接（见上文「把事件推给别的程序」）。

### 放在反向代理后面时，来源地址怎么算

这个前缀自己认反向代理送下来的转发头，不用为它打开 `server.forward-headers-strategy`
（那一项会把控制台与事件流的来源判断一起改掉，不建议为这个前缀去开）：

- 直接连进来的那一端不是本机：来源就是它，请求里写什么转发头都不看。外面的人带一个
  `X-Forwarded-For: 127.0.0.1` 冒充不了本机。
- 直接连进来的是本机、请求里没有转发头：本机直连。
- 直接连进来的是本机、带了转发头：当作经本机上的反向代理进来，**不算本机**（转发头里写着 `127.0.0.1` 也一样），
  来源取转发头里离 NovaBot 最近的那一段（记日志、算无效令牌限速用）——
  `X-Forwarded-For` 取最右一段，`X-Real-IP` 只认一行、一个值，`Forwarded` 取最后一项的 `for=`。
  带了几种就几种都得说的是同一个地址。
- **转发头里只要有一处写得不合规，就当作认不出地址的未知来访者，不会跳过那一处去用别的一段。**
  例如 `X-Forwarded-For` 末尾多了一个逗号、中间有一段不是 IP、端口不在 1–65535；`Forwarded` 的引号里藏了逗号或分号、
  某一项没有 `for=`、带端口或 IPv6 的地址没加引号；几种头说的不是同一个地址。完整的规矩见
  [程序接口约定「来源地址」](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/api.md#来源地址)。
- 若为了控制台开了 `server.forward-headers-strategy: framework`，判法照样：直接连进来的是本机、请求原本不带任何转发头，才算本机直连；
  原本带过 `Forwarded`、`X-Forwarded-For`、`X-Real-IP` 中任何一种的都不算本机，外面的人自带 `Forwarded: for=127.0.0.1` 也冒充不了。
  这时来源取可信代理送来的 `X-Forwarded-For`（与控制台看到的是同一个，见附录 C「控制台的来源地址」），
  `Forwarded`、`X-Real-IP` 不拿来定地址；直接连进来的是本机、却没有能采信的地址时，当作认不出地址的未知来访者。

所以按样板写的反向代理（带上 `X-Real-IP` 与 `X-Forwarded-For`、去掉客户端带来的 `Forwarded`）后面，
外面的人与直连的外面的人一样：那组没打开就是 403；无效令牌的限速也是各算各的，
一个人乱试令牌，不会把同一个反向代理后面的其他人一起限住。
**反向代理一个转发头也不写的话**，经它进来的请求在 NovaBot 看来与本机直连一样，都算本机、开关拦不住——
这样的代理不要拿来转发 `/nova/api/v1/`。反向代理装在另一台机器上时，NovaBot 看到的来源就是那台代理，它不是本机，照开关判。

控制台 `/config` 的来源判断不跟着变：它看的仍是直接连进来的那一端（见附录 C）。
推送接口的「信任反向代理」（`trust-proxy`）只管推送接口，对这个前缀不起作用，不用为它去开。

同一来源 1 分钟内出示无效令牌超过 10 次，之后的无效请求会收到 429，等一会儿自动恢复；
拿着有效令牌的请求不受影响，控制台登录也不受影响。IPv6 来源按 /64 算一个来源。
控制台总开关关掉之后，这个前缀照常能用，只是签不了新令牌、也吊销不了旧令牌（见上文「吊销」）。

## 手动编辑配置文件

`application.yml` 与 `datasource.json` 都可以直接编辑，改完重启即可。
`datasource.json` 的完整示例见发行包里的 `datasource.example.json`。

推送目标的 `type`：**1 为群聊，0 为私聊**。`num` 对 NapCat 是群号或 QQ 号，对官方机器人的群是 NovaBot 分配的编号。`type` 填其他数字会被当作
「未知类型」在运行期丢弃，因此界面在保存时就会拦下；手写 JSON 时没有这道拦，写错了不报错，
只是那条推送悄悄不生效。
