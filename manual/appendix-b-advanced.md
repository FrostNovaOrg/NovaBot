# 附录 B　进阶玩法

正文按「在界面上点」写；这一本附录收那些界面之外、偶尔用得上的东西。

## 处理器类名

[第 6 章](06-add-streamer-and-push.md)的通知开关在界面上点就行，用不到类名。
要用自定义插件提供的处理器、或直接手写配置文件 `datasource.json` 时，才需要
下表的全文类名——文件里要写全限定名，照抄即可：

| 处理器全限定名 | 界面上的名字 | 触发时机 | 可用占位符 |
|---|---|---|---|
| `org.frostnova.nova.bilibili.handler.BilibiliLiveOnPushHandler` | 开播通知 | 开播 | `{uname}` `{title}` `{cover}` `{url}` `{at}` `{next}` `{at=all}` |
| `org.frostnova.nova.bilibili.handler.BilibiliLiveOffPushHandler` | 下播通知 | 下播 | `{uname}` `{time}` `{url}` `{next}` `{at=all}` |
| `org.frostnova.nova.report.handler.BilibiliDynamicPushHandler` | 动态通知 | 动态更新 | `{uname}` `{action}` `{url}` `{picture}` `{at}` `{next}` `{at=all}` |
| `org.frostnova.nova.report.handler.BilibiliLiveReportPushHandler` | 下播报告 | 下播 | `{uname}` `{report}` `{url}` `{next}` `{at=all}` |

**前缀不止一种**：动态通知与下播报告住在报告插件里（`org.frostnova.nova.report.handler.`），
另两个在哔哩哔哩插件里。`{next}` 的意思是「从这里分成两条消息」——在界面的模板
编辑器里不用写它，多建一张卡就是多一条（见第 6 章）。

> [!NOTE] 从 starbot 时代升上来的老配置不用急着改：旧全名（`com.starlwr.bot.`
> 开头的）仍被认，日志里会提醒一句「这个处理器现在叫什么、建议改过来」。
> 其中动态通知与下播报告原先住在哔哩哔哩插件包下，照上表改过来即可，
> 改之前推送照常。

## 每场留下的事件流水

每场直播的明细落在数据目录的 `details/<平台>-<uid>-<开播时刻>/` 下。其中
`events.jsonl` 逐条记下礼物、盲盒、上舰、关注、PK 的开打与结算，一行一条 JSON，
以时刻 `at`（毫秒）与类型 `t` 打头，其余是短键：

| `t` | 含义 | 字段 |
|---|---|---|
| `gift` | 付费礼物 | `uid` 观众、`un` 昵称、`gid` 礼物 id、`gn` 礼物名、`n` 数量、`val` 到手价值、`pay` 实扣、`bag` 是否背包 |
| `box` | 盲盒 | `uid`、`un`、`bn` 投入盒名、`bp` 实扣、`gid`／`gn`／`n` 开出物、`val` 开出面值、`pft` 盈亏 |
| `guard` | 上舰 | `uid`、`un`、`lv` 等级（舰长 3／提督 2／总督 1）、`ot` 开通（1）／续费（2）／未知（-1）、`n` 数量、`u` 单位、`days` 陪伴天数、`val` 价值、`pay` 实扣 |
| `follow` | 关注 | `uid`、`un` |
| `pk_open` | PK 开打 | `pk` 场次号、`tp` PK 类型、`nc` 参加家数、`ps`／`pe` 计划开始与结束（秒）、`op` 对手一串（`r` 房间号、`u` 主播 uid） |
| `pk_settle` | PK 结算 | `pk`、`tp`、`nc`、`er` 提前结算（1／0）、`en` 实际结束（秒）、`mv` 本房票数、`mr` 本房名次、`rs` 本房结果（1 胜／0 负／2 平）、`op` 对手一串（`r`、`u`、`v` 票数、`k` 名次） |

几点读法：

- 上舰的 `ot` 记的是稳定码而不是显示字：1 开通、2 续费、-1 解析不出，旧档里没有这一字段的行按未知读
- 上舰的 `pay` 是实扣；平台未给实付时按 `val` 记
- PK 的票数只是这场的拉票结果，**不算收入**，所以它叫 `mv`／`v` 而不是 `val`／`pay`
- 弹幕与醒目留言的原文在同目录的 `danmu.jsonl`；进场与点赞只计数，不进事件流水
- 进场次数另按分钟记成时序，与其它曲线一起归档在每场的 `detail.json` 里
- 一场最多留 50 万行流水，到了会在日志里说明一声，本场后面的不再收录

## 让事件去触发一个脚本

开播时启动录播、上舰时写一行记录、被切流时给自己发条提醒——这类内置功能覆盖不到的用法，
可以挂一个外部程序：

```yaml
novabot:
  core:
    exec:
      enabled: true          # ⚠️ 默认关闭
      timeout: 30            # 单条命令最长执行时间，单位：秒
      max-concurrent: 4      # 同时执行的命令数上限，超出的直接丢弃
      rules:
        - event: LiveOnEvent
          command:
            - /opt/scripts/record.sh
            - "{room_id}"
            - "{uname}"
```

`event` 填事件类名，简名或全限定名都行，**沿继承链匹配**——填 `LiveOnEvent`
就能同时命中各平台的具体开播事件。可用占位符：
`{event}` `{platform}` `{uid}` `{uname}` `{room_id}` `{timestamp}` `{json}`。

> [!WARNING] `command` 是参数数组，不是一整行命令。第一项是可执行文件，其余各项各自是
> 一个独立参数。想用管道、重定向之类的 shell 特性，请自己写一个脚本文件再在这里填它的路径。
> 这不是写法上的讲究：事件里带的是昵称、弹幕正文这类**完全由陌生人决定**的内容，
> 一旦拼成命令行字符串交给 shell，一个昵称叫 `; rm -rf ~` 的观众就能让你的脚本执行任意命令。
> 走参数数组时，这段文本无论长什么样都只是**一个参数**。

超时会被强制结束；并发超过上限的那次**直接丢弃并记日志**，而不是排队——
等到十分钟后才执行的「开播启动录播」没有任何意义。

## 把事件推给别的程序

把直播间事件按「事件输出协议」实时推给**本机的其他程序**，用于自建面板、独立统计
这类内置功能覆盖不到的场景。它只输出，不接受任何指令：

```yaml
novabot:
  core:
    event-stream:
      enabled: true               # 默认关闭
      path: /nova/events
      buffer-size: 2000
```

打开后地址是 `ws://127.0.0.1:<端口>/nova/events`，与配置界面共用端口。连上后服务端先发
一条 `hello`（带会话标识与能力集），随后是实时事件；每条事件有一个会话内严格递增的 `seq`，
断线重连时用 `resume` 就能把缺的那段补回来。协议的每一帧长什么样、时限是多少，见
[事件源协议](https://github.com/FrostNovaOrg/NovaBot/blob/main/docs/protocol.md)。

> [!NOTE] 这一段以前写在 `starbot.bilibili` 下。事件输出由核心提供，与接的是哪个平台无关，
> 配置也就跟着挪到了 `novabot.core`。5.4 起旧键不再识别；写在旧位置的设置启动时日志会用
> WARN 说明没被读取、该挪到哪，照着挪完重启。

> [!WARNING] **只接受来自本机回环地址的连接，且这一点与 `server.address` 无关。**
> 即使你为了对外提供推送接口把监听地址改成了 `0.0.0.0`，事件流也只认本机。
> 需要从其他机器读取请自行建立 SSH 隧道（`ssh -L 7828:127.0.0.1:7827 你的服务器`）。
> 直接暴露到公网风险自负——这条流里有观众的昵称、uid 与消费金额。

几条口径上的提醒，连上后 `hello` 里的 `notes` 字段也会重复一遍：

- **点赞未聚合**，每次点赞单独一条、`count` 恒为 1
- **`live_state` 没有中途接入的快照**，只在开播、下播、标题变更时下发
- **`source_state` 的 `disconnected` 只在主播被移出数据源时下发**，还在监听列表里时一律是 `reconnecting`
- **房管标志只有弹幕消息带**，其余消息恒为 `false`，含义是「这条消息没说」而不是「不是房管」
- **`emoji` 只在「整条弹幕就是一张表情图」时非空**，判断「这条带表情」要读 `inlineEmojis`
- 每条事件附带平台原始报文（`rawJson`），**字段随平台改版而变，不要当契约用**

**一条连接承载全部房间**，每条信封上都有 `room`，下游必须按它过滤——不滤的后果不只是
「消息多了」：曾有下游把别的主播的礼物一起算进了当前主播的本场累计，主播看到一个错的数字
而界面上没有任何提示。`seq` 也是整条连接共用的，所以过滤时**只能丢消息，不能丢序号**：
按 `room` 筛掉几条之后，本房间的下一条 `seq` 自然不连续，把它当跳号处理就会凭空报出一次
不存在的断档。判断有没有真丢包，要看**整条连接**的 `seq` 连不连续。

缓冲是全部房间共用的一条流。房间多或弹幕密时要把 `buffer-size` 调大，否则客户端重连时会
被告知补不上而必须清空重来；每条约数 KB，调大前先掂量内存。

**开了口令时（`require-token: true`）客户端要先开口。** 口令只在连接建立后的第一帧出示：

```json
{"kind":"auth","token":"<口令>"}
```

认证成功之前服务端什么都不发，连 `hello` 也不发——所以别等 `hello` 再发口令，会一直等
到 10 秒后被断开。口令在配置控制台签发（只读），**明文只在签发那一刻显示一次**；
签发时要填「签给谁」，否则日后无法单独吊销。吊销对已经建立的连接不自动生效，
撤完要确认对方确实掉线了。握手里带 `Sec-WebSocket-Protocol` 或 `Authorization` 一律拒收
（HTTP 400），`?token=` 查询参数也不接受——凭据不进 HTTP 工件，免得落进反向代理的访问日志。

## 手动编辑配置文件

`application.yml` 与 `datasource.json` 都可以直接编辑，改完重启即可。
`datasource.json` 的完整示例见发行包里的 `datasource.example.json`。

推送目标的 `type`：**1 为群聊，0 为私聊**，`num` 是对应的群号或 QQ 号。填其他数字会被当作
「未知类型」在运行期丢弃，因此界面在保存时就会拦下；手写 JSON 时没有这道拦，写错了不报错，
只是那条推送悄悄不生效。
