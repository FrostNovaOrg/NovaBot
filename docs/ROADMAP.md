## 存储方案：Redis 可选（2026-08-04 已决策）

**结论：配了 Redis 就有完整的累计数据，没配则降级为只有本场数据。**

`LiveDataService` 本就是可替换的扩展点，因此：

- **未配置 Redis**（默认）：沿用 `DefaultLiveDataService`（JSON）。
  本场数据完整可用——排行榜、本场个人数据都能出；
  累计类能力（`我的总数据`、`直播间总数据`）明确提示需要配置 Redis，
  **不静默返回 0**，那会让人以为是数据丢了
- **配置了 Redis**：启用 `RedisLiveDataService`，本场 + 累计双份，
  键设计对齐上游（zset 存 uid → 分数，天然支持排行榜与个人查询）

这样既不强迫普通使用者部署外部服务，又给重度使用者留了完整能力。
降级边界必须在界面与命令回复中说清楚，这是本方案唯一的风险点。

### 决策过程（备查）

**这是第一阶段的前置问题，绕不开。**

Python 版用 Redis 存两套数据：

- **本场**：`RoomDanmuCount:{room}`、`UserDanmuCount:{room}`（zset：uid → 分数）
- **累计**：`RoomDanmuTotal:{room}`、`UserDanmuTotal:{room}`，下播时由本场并入

本项目当前只有一个 `data.json`，整体载入内存、每 5 分钟全量序列化落盘。
**本场数据放 JSON 没问题**（单场有天然上界），但累计数据会无限增长：

> 粗算：一个活跃直播间单场约数千名弹幕用户，累计可达数万至数十万。
> 每条「uid → 分数」在 JSON 中约 30 字节，5 类指标 × 3 个直播间 × 10 万用户
> ≈ 45 MB。这份文件每 5 分钟要全量序列化一次，且常驻内存——
> 在 4 GB 的小机器上不可接受。

三个可选方向：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 引入 SQLite | 单文件、无需外部服务 | 新增 JDBC 依赖与一层数据访问代码 |
| B. 按直播间拆分 JSON | 改动最小 | 只是把问题推后；单个热门直播间仍会撑大 |
| **C. 可选 Redis**（已采纳） | 与上游一致、性能最好；做成可选后不影响普通使用者 | 重度使用者需部署 Redis；降级边界要讲清楚 |

采纳 C。理由是它对普通使用者零负担（不配就用 JSON，本场能力完整），
同时给重度使用者与上游一致的完整能力；而 A 虽无外部依赖，
却要为所有人引入一层数据访问代码，收益并不对称。

## 第四阶段：绑定与数据查询

- [x] `绑定` — QQ 号绑定 B 站 UID，含二次确认（上游用的是一分钟内回复「确认绑定」）
- [x] `我的数据` / `我的总数据` — 查本人在该直播间的贡献
- [x] `直播间数据` / `直播间总数据` — 查直播间统计
- [x] `数据排行榜` — 群内贡献榜，带翻页
- [x] 查询结果同样以图片呈现（复用报告绘图组件）

**已实现（2026-08-05）**：以上全部，外加 `解绑` 与 `总数据排行榜`，共 9 条命令。
查询结果统一走 `BilibiliDataQueryPainter` 出图。命令数上到 20 条后，
`菜单` 改为按分类分组展示（`StarBotCommand.category()`）。

两处与上游的取舍差异，都是有意为之：

- **绑定不做归属验证**。没有接口能证明 QQ 号与哔哩哔哩账号属于同一人，
  两步确认核对的是「uid 有没有打错」。上游同此，但代码与文档里说清楚了这一点
- **翻页不走带偏移量的接口**。取到本页末尾再截取即可：JSON 实现本就要全量排序，
  Redis 的 zset 取前 N 名也很廉价，为翻页在 `LiveDataService` 上再开一个方法不划算

**验收**：单元测试已覆盖参数解析、翻页边界、降级提示与出图（含版面样张）。
**真机验收待做**——绑定后查得到自己的数据、且与报告里的排行榜数值一致，
这一条要等下一场真实直播。

## 第五阶段：曲线图与变化量

成本最高的一阶段，需要新的时序采样与额外接口。

- [x] 时序存储：按时间分桶记录各类互动，供绘制曲线（一分钟一格，随本场数据清零）
- [x] 五类互动曲线：弹幕、礼物、SC、盲盒、大航海
- [x] 盲盒盈亏也一并入时序（`box_profit`），面积按绝对值取比例
- [x] 粉丝数、粉丝团人数、大航海数：开播记快照，出报告时取实时值相减
- [x] 需补的接口：粉丝数、粉丝团人数、大航海人数

**已实现（2026-08-05）**。三处实现选择值得记一笔：

- **每条曲线各画一张、各按自身峰值缩放**，不叠在同一张图上。弹幕以「条」计、
  礼物以「元」计，量级动辄差两个数量级，共用纵轴的结果是除最大的那条外全被压成直线
- **重采样两个方向都要处理**。时间格数与像素列数几乎不会相等：三小时的直播只有 180 格
  却有四百多列，只把有数据的格落到对应列会画出一排竖齿（初版就是这样，看样张才发现）；
  十二小时则反过来多格挤一列。做法是先补成逐格的稠密数组，再按列取所辖各格的最大值——
  取最大而非平均，短促的高峰才不会被摊平，也与标题上的「峰值 X/分」自洽
- **变化量不单独记终值**：开播记快照，绘制时取实时值相减。于是直播中随时拉的实时报告
  与下播报告共用同一段逻辑，也不必担心「记终值」和「画报告」两步之间的顺序

三个接口均已对真实账号验证（测试主播 uid 3000000000000001，房间 2000000001），
无需登录态：粉丝数复用已有的 `live_user/v1/Master/info` 的 `follower_num`（243），
粉丝团人数取 `rank/getFansMembersRank` 的 `data.num`（36），
大航海人数取 `guardTab/topList` 的 `data.info.num`（3）。

**真机验收待做**：报告图里的曲线横轴与直播时段吻合、涨幅与直播间实际变化一致。

## 第六阶段：报告版式配置化

- [x] 报告各区块可独立开关（11 项，对齐上游 `LiveReport` 的布尔配置）
- [x] 配置界面中可视化勾选
- [x] 自定义 logo（`starbot.bilibili.live.report-logo-path`）

**已实现（2026-08-05）**。做成了**通用机制**而非给报告写死一个面板：
处理器在 `StarBotEventHandler.options()` 里声明自己有哪些参数
（`HandlerOption`：键、名称、说明、类型、默认值、取值区间），
界面按类型渲染开关与数字框，本身不认识任何具体参数名——
因此第三方插件声明了 `options()` 就同样能在界面上配。

两处刻意的约束：

- **默认值只有一处出处**。`getDefaultParams()` 由 `OPTIONS` 派生，不再各写一份。
  两处各写一份的话，改了一处忘了另一处，界面上勾的与实际生效的就会对不上，
  而这种不一致不会有任何报错，只会让人以为「配了没用」。已有测试守住这条
- **界面当场把数字夹到合法区间**。后端本来也会夹，但界面允许填 21 而绘制时夹到 20，
  等于界面在骗人。取值区间与 `BilibiliLiveReportOptions` 一致，同样有测试守住

**已本地真跑验证**（起本地实例 + 浏览器面板）：11 项全部渲染正确、
勾选与数字改动能存进 `datasource.json`、超限值当场夹回、刷新后读得回来，
且**只有改动过的项会被写入**——没碰过的项继续跟随处理器的默认值。
过程中发现并修掉一个版式 bug：`.target input` 的 150px 宽度把勾选框撑掉了整格，
导致标签换行、数字行互相重叠。

## 推进原则

- 每阶段独立可用、独立发布，不留半成品
- 涉及外部接口的功能一律真机验证，「离线测试全绿」不等于能用
- 数据结构变更要考虑既有 `data.json` 的兼容，不能让使用者升级后丢数据
