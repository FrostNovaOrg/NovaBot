分多个阶段推进，每个阶段独立可用、可单独发布。

> 依据：上游 Python 版仓库 `Starlwr/StarBot`（分支 `python`）的
> `starbot/commands/builtin/`、`starbot/painter/LiveReportGenerator.py`、
> `starbot/utils/redis.py` 与 `starbot/core/model.py`，于 2026-08-04 查阅。

## 存储方案：Redis 可选（2026-08-04 已决策）

**结论：配了 Redis 就有完整的累计数据，没配则降级为只有本场数据。**

`LiveDataService` 本就是可替换的扩展点，因此：

- **未配置 Redis**（默认）：沿用 `DefaultLiveDataService`（JSON）。
  本场数据完整可用——排行榜、本场个人数据都能出；
  累计类能力（`我的总数据`、`直播间总数据`）明确提示需要配置 Redis，
  **不静默返回 0**，那会让人以为是数据丢了
- **配置了 Redis**：启用 `RedisLiveDataService`，本场 + 累计双份，
  键设计对齐上游（zset 存 uid → 分数，天然支持排行榜与个人查询）

这样既不强迫普通使用者部署外部服务，又给重度使用者留了完整能力。
降级边界必须在界面与命令回复中说清楚，这是本方案唯一的风险点。

### 决策过程（备查）

**这是第一阶段的前置问题，绕不开。**

Python 版用 Redis 存两套数据：

- **本场**：`RoomDanmuCount:{room}`、`UserDanmuCount:{room}`（zset：uid → 分数）
- **累计**：`RoomDanmuTotal:{room}`、`UserDanmuTotal:{room}`，下播时由本场并入

本项目当前只有一个 `data.json`，整体载入内存、每 5 分钟全量序列化落盘。
**本场数据放 JSON 没问题**（单场有天然上界），但累计数据会无限增长：

> 粗算：一个活跃直播间单场约数千名弹幕用户，累计可达数万至数十万。
> 每条「uid → 分数」在 JSON 中约 30 字节，5 类指标 × 3 个直播间 × 10 万用户
> ≈ 45 MB。这份文件每 5 分钟要全量序列化一次，且常驻内存——
> 在 4 GB 的小机器上不可接受。

三个可选方向：

| 方案 | 优点 | 代价 |
|---|---|---|
| A. 引入 SQLite | 单文件、无需外部服务 | 新增 JDBC 依赖与一层数据访问代码 |
| B. 按直播间拆分 JSON | 改动最小 | 只是把问题推后；单个热门直播间仍会撑大 |
| **C. 可选 Redis**（已采纳） | 与上游一致、性能最好；做成可选后不影响普通使用者 | 重度使用者需部署 Redis；降级边界要讲清楚 |

采纳 C。理由是它对普通使用者零负担（不配就用 JSON，本场能力完整），
同时给重度使用者与上游一致的完整能力；而 A 虽无外部依赖，
却要为所有人引入一层数据访问代码，收益并不对称。

## 第一阶段：数据模型升级（地基）

没有这一层，后面四个阶段都做不了。

- [x] ~~确定累计数据的存储方案~~ → Redis 可选（见上）
- [ ] `LiveDataService` 增加按用户计分的能力：
      `incrementUserMetric(platform, uid, metric, userUid, delta)`、
      `getUserScore(...)`、`getTopUsers(..., limit)`、`getUserCount(...)`
- [ ] 本场与累计双份：下播时把本场并入累计（对应上游的 `zunionstore`）
- [ ] 现有的 `recordLiveMetricUser`（只记人数、不记分）迁移到新接口，
      语义上它是「分数恒为 1」的特例
- [ ] 容量保护：单直播间用户数上限、超限策略要显式且有日志，不能静默丢数据
**Redis 实现挪至第四阶段之前**（2026-08-04 调整）：它只服务于累计数据，
而累计数据的唯一消费方是第四阶段的 `我的总数据` / `直播间总数据`。
第二阶段的排行榜用的全是本场数据，JSON 已足够。先做没人用的东西不划算，
接口已按可插拔设计好，届时补实现不影响既有代码。

- [ ] （移至第四阶段前）`RedisLiveDataService` 实现，键设计对齐上游
- [ ] （移至第四阶段前）累计查询的降级提示与健康探针中的存储后端展示

**验收**：单元测试覆盖本场/累计的累加与并入；真机跑一场直播后，
能查出某个用户发了多少条弹幕。

## 第二阶段：报告增强（排行榜与名单）

数据齐了之后，这一阶段纯粹是绘图与配置。

- [ ] 五类排行榜：弹幕、礼物、SC、盲盒数量、盲盒盈亏
- [ ] 大航海名单（本场新开通的观众）
- [ ] 每类排行榜可配置显示前 N 名，`0` 为不显示（与上游一致）
- [ ] 头像获取：排行榜要显示用户头像，需批量拉取并缓存，注意接口频率

**验收**：真机下播后报告图含排行榜，人数不足时版面自动收紧。

## 第三阶段：命令系统与 @我 订阅

地基已在上一轮铺好：`StarBotRemoteMessageEvent` 事件总线（OneBot 适配器
把群消息发布到事件总线）。本阶段把它扩展成完整的命令框架。

- [ ] 命令注册与分发框架：统一前缀（可配置）、命令名、参数解析、帮助文本
- [ ] `菜单` — 列出可用命令
- [ ] `启用命令` / `禁用命令` — 按群控制，需要一份「群 → 已禁用命令」存储
- [ ] `开播@我` / `取消开播@我` / `开播@名单`
- [ ] `动态@我` / `取消动态@我` / `动态@名单`
- [ ] 推送时把订阅者拼进 `{at}` 占位符

**验收**：群里发命令能订阅，下次开播时确实被 @ 到。

## 第四阶段：绑定与数据查询

- [ ] `绑定` — QQ 号绑定 B 站 UID，含二次确认（上游用的是一分钟内回复「确认绑定」）
- [ ] `我的数据` / `我的总数据` — 查本人在该直播间的贡献
- [ ] `直播间数据` / `直播间总数据` — 查直播间统计
- [ ] `数据排行榜` — 群内贡献榜，带翻页
- [ ] 查询结果同样以图片呈现（复用报告绘图组件）

**验收**：绑定后查得到自己的数据，与报告里的排行榜数值一致。

## 第五阶段：曲线图与变化量

成本最高的一阶段，需要新的时序采样与额外接口。

- [ ] 时序存储：按时间分桶记录各类互动，供绘制曲线
- [ ] 五类互动曲线：弹幕、礼物、SC、盲盒、大航海
- [ ] 盲盒盈亏曲线（上游单独有一条 `BoxProfitRecord`）
- [ ] 粉丝数、粉丝团人数、大航海数的开播/下播快照与差值
- [ ] 需补的接口：粉丝数、粉丝团信息、大航海列表

**验收**：报告图含曲线，横轴时间与直播时段吻合。

## 第六阶段：报告版式配置化

- [ ] 报告各区块可独立开关（对齐上游 `LiveReport` 的十余个布尔配置）
- [ ] 配置界面中可视化勾选
- [ ] 自定义 logo

**验收**：关掉某区块后报告图不再包含它，且版面无空洞。

## 不打算照搬的部分

- **上游的存储假设**（Redis + MySQL）：与本项目「装上就能用」的定位冲突，
  改用文件型方案实现同等能力
- **上游的 QQ 框架**（Mirai / Ariadne）：本项目走 OneBot 协议，不迁移
- **赞赏 / 官网相关**：与本 fork 无关

## 推进原则

- 每阶段独立可用、独立发布，不留半成品
- 涉及外部接口的功能一律真机验证，「离线测试全绿」不等于能用
- 数据结构变更要考虑既有 `data.json` 的兼容，不能让使用者升级后丢数据
