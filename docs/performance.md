# 资源占用与调优

## 实测数据

下列数字为本仓库在 **macOS / JDK 17.0.20 / 默认启动参数** 下的实测值，测量方法与条件一并列出，
以便在自己的环境中复现或对照。

### 测量条件

- 启动参数：`start.sh` 的默认值（`-Xms128m -Xmx512m -XX:+UseSerialGC -Xss256k`）
- 已加载插件：OneBot 适配器、NapCat 扩展、哔哩哔哩插件
- **未连接任何直播间**（`enable-connect-live-room: false`），未登录哔哩哔哩账号
- 采样方式：启动完成并静置后，每 5 秒读一次 `ps -o rss=`，取多次读数

### 结果

| 指标 | 数值 |
|---|---|
| 稳态常驻内存（RSS） | 53 – 66 MB |
| 启动瞬时峰值 | 190 MB 左右（类加载期间，随后回落） |
| GC 后堆实际使用 | 不足 1 MB |
| 线程数 | 42 |
| 空闲 CPU | 低于 1% |

启动期的峰值来自类加载与 Spring 容器初始化，属于一次性开销，不代表长期占用。
只看单次采样很容易被这个峰值误导——上表的数字是静置后多次采样得到的。

### 未覆盖的部分

**每个直播间长连接会在上述基线之上带来额外开销**，包括一个 WebSocket 会话、消息缓冲区
以及事件对象的分配。这部分需要真实登录哔哩哔哩账号才能测量，本文未做实测，因此不给出具体数字。
弹幕活跃的大型直播间开销明显高于冷清的直播间，请以自己的实际部署为准。

动态图片绘制是唯一的 CPU 突发点：绘制期间单核占用会短时升高，持续约一到数秒，之后回落。

## 已做的优化

相比上游默认配置，本仓库做了以下调整，均已体现在默认值中：

| 项目 | 上游 | 本仓库 | 原因 |
|---|---|---|---|
| 核心网络线程池 | 10 / 50，队列 5 | 4 / 24，队列 64 | 队列过小会让任务直接催生新线程 |
| OneBot 线程池 | 10 / 100，队列 0 | 2 / 16，队列 128 | 队列容量为 0 时每个任务都可能新建线程 |
| 哔哩哔哩线程池 | 10 / 100，队列 0 | 4 / 32，队列 256 | 同上 |
| Tomcat 工作线程 | 200（框架默认） | 8 | StarBot 只服务推送接口与配置界面 |
| 线程栈 | 1 MB（平台默认） | 256 KB | 调用栈很浅，几十个线程下可省下数十兆 |
| 直播间 WebSocket 客户端 | 每个直播间一个 | 全部共享一个 | 每个客户端各带一套容器与线程池 |
| 动态绘图画布 | — | 按需扩展 | 初始按「足够高」分配会一次性吃掉数百兆 |

此外还修复了一处会直接占满 CPU 的缺陷：**OneBot 长连接重连原本会退化为满核空转**
（详见 CHANGELOG）。OneBot 服务未启动时，上游实测 30 秒内重试逾 61 万次；修复后 40 秒内仅重试 4 次。

其中后两项对内存影响最大：

- **共享 WebSocket 客户端**：`StandardWebSocketClient` 每个实例都会创建独立的 WebSocket 容器与
  线程池。上游为每个直播间新建一个，监听 N 个直播间就有 N 套线程池。
- **绘图画布按需扩展**：画布是 `TYPE_INT_ARGB` 位图，每像素 4 字节。若按 900×100000 直接分配，
  单次绘制就要 360 MB，在小内存机器上必然 OOM。

## 进一步压低占用

### 缩小堆

监听的直播间不多时可以压得更低：

```bash
JAVA_OPTS="-Xms96m -Xmx320m" ./start.sh
```

不建议低于 256 MB：绘制多图动态时需要同时持有若干张解码后的位图。

### 关闭不需要的功能

| 配置项 | 效果 |
|---|---|
| `starbot.bilibili.live.only-connect-necessary-rooms: true` | 只连接订阅了直播事件的直播间 |
| `starbot.bilibili.live.enable-connect-live-room: false` | 完全不连长连接，仅靠轮询判断开播下播；代价是收不到弹幕、礼物等事件 |
| `starbot.bilibili.live.complete-event: false`（默认） | 不为事件补全昵称头像，显著减少接口请求 |
| `starbot.core.config-ui.enabled: false` | 配置完成后可关闭配置界面 |

### 应用类数据共享

把类元数据预先归档，可缩短启动时间：

```bash
java -XX:ArchiveClassesAtExit=starbot.jsa -Dloader.path=lib,plugins-lib -jar StarBotCore.jar
```

之后启动时带上归档：

```bash
java -XX:SharedArchiveFile=starbot.jsa -Dloader.path=lib,plugins-lib -jar StarBotCore.jar
```

## 关于用其他语言重写

结论：不建议。

常驻内存的绝大部分来自 JVM 与 Spring 容器本身——GC 后堆实际使用不足 1 MB，说明业务对象
占比极小。真正吃 CPU 的只有动态图片绘制，而那是短促的突发负载。把绘制部分改用 Rust 之类的
语言实现，需要引入 JNI 或外部进程通信，给一个插件化的 Spring 应用增加跨语言边界，
复杂度显著上升，却省不下那几十兆的基座开销。

如果确实需要把内存压到更低，正确的方向是 GraalVM 原生镜像而不是换语言——Spring Boot 4 原生支持，
可将常驻内存进一步降低并把启动时间压进毫秒级。

代价是：反射与动态类加载需要额外的配置提示文件，而本项目的插件机制正是基于运行期类加载，
适配工作量不小，且构建产物与平台绑定。目前未提供原生镜像构建，需要的话可自行尝试：

```bash
mvn -Pnative native:compile
```
