# 排障与 FAQ

先看**总览页的健康自检**。每一项异常都会给出具体的修复建议，而不只是「异常」二字。
本文补充自检覆盖不到的情况。

## 排障总原则

这类工具最难查的地方在于：**多数错误的表现完全一样——什么都不发生**。
所以排查顺序应该是从后往前，逐段确认链路：

```
哔哩哔哩 ──①──▶ NovaBot ──②──▶ OneBot 实现 ──③──▶ QQ 群
```

1. 先在「机器人」页**发一条测试消息**。收到 → ②③ 段是通的，问题在采集侧；收不到 → 问题在投递侧
2. 收不到时看测试消息回显的**接口原始响应**，它会直接告诉你是 Token 不对、群号不存在还是没在群里
3. 采集侧的问题看「哔哩哔哩」页的登录状态与直播间连接数

## 一、配置界面打不开

**日志里的地址打不开** — 界面默认只监听 `127.0.0.1`。装在远程服务器上时要先建隧道：

```bash
ssh -L 7827:127.0.0.1:7827 用户名@服务器地址
```

然后在自己的电脑上打开日志里的那个地址。**不要改成 `0.0.0.0` 暴露到公网**。

**提示令牌无效** — 令牌默认每次启动重新生成，重启后要用新日志里的地址。
想固定下来就在配置里写死 `starbot.core.config-ui.token`（别用 `test`、`123456` 这类弱口令，启动会告警）。

**程序压根没起来** — 见下一节。

## 二、程序启动失败

**配置文件写坏了** — NovaBot 会自动进入**安全模式**：一个只提供「看 / 改 / 回滚
`application.yml`」的极简页面，地址与令牌同样打印在日志里。用它回滚到上一份备份即可。

安全模式是独立于主程序的最小实现，所以主程序起不来时它仍然能用。

**端口被占用** — 改 `server.port`，或找出占用进程：

```bash
lsof -i :7827
```

**Java 版本不对** — 需要 17 或更高：

```bash
java -version
```

## 三、消息推不出去

按测试消息回显的原始响应对号入座：

| 现象 | 原因 | 怎么修 |
|---|---|---|
| HTTP `Token 不正确` | `one-bot-http-token` 与 OneBot 实现里配的不一致 | 两边核对，注意首尾空格 |
| HTTP `连不上` | OneBot 实现没启动，或地址端口填错 | 确认 NapCat 在跑；确认填的不是 Websocket 端口 |
| HTTP `服务异常` | OneBot 实现自身状态异常，通常是 QQ 掉线了 | 去 NapCat 那边重新登录 QQ |
| 接口返回成功但群里没有 | 机器人不在该群，或群号填错 | 确认机器人已入群；核对群号 |
| WS `连不上`（HTTP 正常） | 只影响接收群内事件，**不影响推送** | 不急着修；需要弹幕类插件时再处理 |

**私聊收不到但群聊正常** — 检查目标类型的取值：**1 是群聊，0 是私聊**。
填成 2 之类的数字会被当作「未知类型」在运行期直接丢弃。界面保存时会拦下，手写 JSON 时不会。

**@全体成员没生效** — 要求机器人是群主或管理员，且每天有次数限制。
装了 NapCat 扩展插件时，次数用尽会自动改用群待办。详见第五节。

## 四、直播 / 动态不推送

**开播了但没推** — 依次确认：

1. 「推送规则」里这位主播的开关是开着的，且勾选了「开播」
2. 「哔哩哔哩」页显示的直播间连接数正常
3. 总览页的「全局推送」不是暂停状态
4. 当前不在静音时段内（`quiet-start` / `quiet-end`）

直播间连接被数据风控时，自检会显式说明。此时可关闭长连接（`enable-connect-live-room: false`），
改用备用直播推送——那是轮询直播状态，延迟更高但不依赖长连接。

**动态不推但直播正常** — 动态需要登录态，直播不需要。看「哔哩哔哩」页的登录状态。
掉登录时重新扫码即可。

**动态推送延迟很大** — 动态是轮询的，延迟取决于轮询间隔。间隔调太小容易触发风控，不建议。

**推了但图片是空的** — 动态图片是本地绘制的，看日志里绘图相关的报错。
若字体文件缺失，图片会渲染异常。

## 五、群里的命令与数据

**机器人对命令毫无反应** — 按可能性从高到低：

1. **这个群没配推送**。机器人只在已配置推送目标的群里应答，其他群一律沉默——
   这是有意的，否则拉进任何群都会被人当机器人用
2. **命令被人关掉了**。群主或管理员在群里发过 `禁用命令 xxx`。
   控制台「群与成员」页能看到每个群关了哪些，也能直接改回来。
   **不看那一页无从分辨「坏了」还是「被关了」**，两者表现完全一样
3. **不是以命令名开头**。「我想看看我的数据」不会触发，`我的数据` 才会
4. **3 秒冷却**。同一个群刚响应过一条命令

**发「禁用命令」被拒** — 只有群主、群管理员，或 `starbot.core.command.admins`
里列出的超管能用。机器人的主人未必是每个群的管理员，把自己的 QQ 号填进那份名单即可，
它跨群生效。**私聊里一律不算管理员。**

**「我的总数据」说需要 Redis** — 带「总」字的命令要跨场次累计，只有 Redis 实现支持。
设置页搜 `spring.data.redis.host` 填上地址，重启即可。没配时它明说不可用，
而不是回一堆 0——**那样会让人误以为数据丢了**。

**本场数据是对的，累计是 0** — 累计在**下播那一刻**才并入。这一场还没结束时，
累计里自然没有本场的份。

**`@全体成员` 没发出来，正文倒是发了** — 机器人在那个群不是群主或管理员。
这是**程序主动摘掉的**：QQ 服务端这一路不做客户端那道权限检查，
硬发能成功，但绕过权限强行 @ 全体有账号风控风险，代价是整条推送链路停摆。
把机器人设为管理员，或接受只发正文。

日志里搜「@全体成员」能看到是哪一种情况：没权限被摘掉，还是**当日额度用完**
（账号 10 次/天全群共享、单群 20 次/天，两者独立记）。

**数据分析页是空的** — 归档从 4.1.0 起才有，**之前的直播不会追溯**，
且只在下播时追加。播完一场之后就有内容了。
若播完仍是空的，看日志里有没有「没有记录到开播时间, 本场不归档」——
程序在直播中途才启动时会这样，一条没有起点的记录算不出时长，留着只会污染统计。

## 六、账号相关

**过一段时间就掉登录** — 4.0.0 起扫码登录改走 TV 端接口，会连同 Cookie 一并返回可续期的令牌
（有效期 180 天，到期前 30 天自动续期），正常情况下不该再掉。
启动日志里搜「可自动续期的登录令牌」能看到到期日期。

若健康自检显示「未取得刷新口令，无法自动续期」，说明这份凭据是用旧版本或
`qr-code-login-mode: web` 扫出来的——**退出登录重新扫一次**即可换成可续期的。

**掉得比这频繁得多** — 那就不是凭据到期的问题：

- 同一账号不要同时在多处登录 Web 端，会互相挤下线
- 账号被风控时任何客户端都会掉，先去网页端确认账号状态正常
- 日志里搜「登录态」，看复检是在哪一步判定失效的

**每次重建容器都要重新扫码** — 卷没挂对。凭据写在工作目录下，卷必须挂在 `/app`，
挂到 `/app/data` 之类的子目录不会持久化任何东西。见[用户手册的容器部署](user-guide.md#容器部署)。

**二维码扫不出来** — 终端里的字符画二维码受字体与终端宽度影响。
改用**配置界面的「哔哩哔哩」页**扫，那里是真图片。

**想换账号** — 「哔哩哔哩」页点「退出登录」，再扫新账号的码。
或直接删掉 `cookies.json` 与 `cookies.key` 后重启。

## 七、资源占用

**内存比文档写的高** — 先确认测量方式。**强制 GC 后读到的 RSS 会偏高**（Full GC 会触碰所有页），
不能当稳态值。正确做法是让程序空跑一段时间后直接读 RSS。

内存偏高时可用环境变量覆盖，不必改文件（容器里用 `-e JAVA_OPTS=...`）：

```bash
JAVA_OPTS="-Xmx256m" ./start.sh
```

注意 `-Xms` 会被提前提交，调大反而抬高常驻内存。
若同时用 systemd 部署，调低 `-Xmx` 后记得一并调低单元文件里的 `MemoryHigh` / `MemoryMax`——
反过来，只压 cgroup 上限而不动 `-Xmx`，会让进程在堆涨起来时被内核直接杀掉。

**CPU 占用高** — 通常来自直播间长连接的心跳与动态轮询。监听的主播多时属正常；
可关闭长连接改用备用推送来降低开销。

# FAQ

**要不要专门准备一个 QQ 小号？**

要。发消息的是 OneBot 实现登录的那个 QQ，用你的主号有被风控的风险。

**哔哩哔哩账号必须登录吗？**

只推直播的话不需要——直播状态是公开信息。**动态推送需要登录**。
建议用小号，原因见 [SECURITY.md](../SECURITY.md)。

**会不会被封号？**

本项目只调用哔哩哔哩的公开接口，请求频率也做了限制。但任何自动化都存在风控风险，
所以建议用小号。

**可以同时推给多个群吗？**

可以。一位主播下可以加任意多个推送目标，每个目标的事件与模板都能单独配置。

**可以监听多位主播吗？**

可以，数量没有硬限制。主播多时直播间长连接会更多，内存与 CPU 会相应上升。

**推送内容能自定义吗？**

能。在「推送规则」里勾选事件后点「编辑模板」，占位符可点击插入，右侧实时预览。

**能不能只在特定时间推送？**

设置里有静音时段（`quiet-start` / `quiet-end`），支持跨零点。
想临时全停就用总览页的「暂停全部推送」，立即生效。

**改了配置要重启吗？**

大部分要。「暂停全部推送」是例外，立即生效。

**上游 StarBot 的插件能用吗？**

能。包名、构件坐标与配置键都刻意保持了兼容。

**升级会丢配置吗？**

不会。替换程序文件即可，`application.yml` 与 `datasource.json` 保留原样。
从上游 beta8 迁移需要改一处，见[用户手册的升级章节](user-guide.md#8-升级)。

**直播数据会一直留着吗？**

分三份。**本场数据**在下次开播时清零；**累计数据**永久保留，但需要配置 Redis；
**每场的归档**（`sessions.jsonl`）永久保留且只增不删，是「数据分析」页的数据源。
想做别的分析可以直接拿这个文件走，每行一条 JSON。

**能查历史某一场的详细数据吗？**

「数据分析」页给的是按周 / 月的汇总。单场的完整记录在 `sessions.jsonl` 里，
但界面上没有单场视图。**报告图不会留存**，它是推送时现画的。

**群成员的绑定关系、订阅名单存在哪？**

`state.json`，可在控制台「群与成员」页查看与清理。**它不进备份脚本的话就没人备份**，
换机器时记得一起带走。

**日志在哪？**

systemd 部署：`sudo journalctl -u starbot -f`。手动运行：直接输出到终端。

**怎么知道推送到底有没有成功？**

总览页有「最近推送」列表，包含时间、目标、内容摘要与结果；失败会写明原因。

**出了问题能主动通知我吗？**

能，配置 `starbot.core.alert` 把告警发到你的 QQ。
注意 `qq-type` 是 **1 群聊 / 0 私聊**。

**和上游 StarBot 是什么关系？**

本仓库是上游的整理版本，遵循 AGPL-3.0，含一项推送接口鉴权的安全修复。
详见 [NOTICE](../NOTICE) 与 [CHANGELOG.md](../CHANGELOG.md)。

## 提问前请准备

自检和上面都没解决时，附上这些信息更容易得到帮助：

1. 总览页健康自检的**截图**
2. 「机器人」页发送测试消息后的**原始响应**
3. 相关时间段的日志（**记得抹掉 Token、cookies、群号等敏感内容**）
4. NovaBot 版本与 OneBot 实现的名称版本
