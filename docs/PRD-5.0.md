# NovaBot 5.0 产品开发与重构需求文档

> 整理日期 2026-08-06。基线版本 4.2.0（已部署）。
> 来源：① 弹幕发送能力调研 ② 开放平台双源可行性 ③ 31 个同类仓库的横向梳理。
> 本文只写「做什么、为什么、代价多少」，不写实现细节。

---

## 0. 三个先给答案的结论

**一、自动欢迎弹幕：上下游都没有，要做就是从零做，而我建议基本不做。**
本仓库零发送能力；上游 Python StarBot 有 `send_danmaku` 这个方法但**一个调用点都没有**。
这条赛道上功能最全的 MagicalDanmaku（1242 星）已于 2025-12-25 由作者主动永久归档。

**二、开放平台能接，但 `open_id ≠ uid` 是一道过不去的墙。**
可以校准聚合量、可以做掉线接续，**但观众级别的数据无法跨源合并**——
同一个观众在两个源里就是两个人。所以正确的形态是「主从 + 分层」，不是「两源合一」。

**三、31 个仓库里真正值得抄的是五六个具体设计，不是整套架构。**
其中优先级最高的一条是数据正确性问题：**「主动下播」和「被切流」现在没有分开**。

## 一、弹幕发送能力评估

### 1.1 本仓库：零

枚举了 `BilibiliApiUtil` 里全部 24 个接口常量，写操作只有一个
`RELATION_MODIFY_API`（关注/取关）。**没有 `msg/send`，没有任何形式的弹幕发送。**

### 1.2 上游 Python StarBot：有能力，无功能

| 位置 | 内容 |
|---|---|
| `starbot/core/live.py:368` | `LiveRoom.send_danmaku(danmaku)` → `POST https://api.live.bilibili.com/msg/send` |
| `starbot/core/live.py:406/531/569` | `send_gift_from_bag` / `send_gift_gold` / `send_gift_silver` |
| `starbot/core/live.py` | `add_block` / `del_block`（房管禁言）、`sign_up_dahanghai`（大航海签到） |
| `starbot/core/user.py:347` | `send_msg`（私信） |
| `starbot/utils/Danmaku.py` | 弹幕数据类，含 `Mode`（飞行/顶部/底部/逆向）与 `FontSize` 枚举 |

**全仓库 grep 的结论：这些方法的调用点为零。** 它们是从 `bilibili-api` 继承下来的接口层，
属于死代码。上游从来没有做过自动欢迎、答谢或任何主动发送的功能。

> 也就是说，「StarBot 有弹幕欢迎功能」这个印象是不成立的。要做只能从零做。

### 1.4 Bilibili_Danmuji 的设计（同为 Java + SpringBoot，最值得读）

**配置模型** —— `ThankWelcomeSetConf` 及其基类 `ThankLiveSetConf`：

| 字段 | 作用 | 为什么重要 |
|---|---|---|
| `welcomes = "欢迎%uNames%的进入直播间~"` | 模板 + **复数**占位符 | 多个人合并进一条弹幕 |
| `list_people_shield_status` | 0 全部 / 1 仅勋章 / 2 仅舰长 | **谁值得欢迎**——全员欢迎就是刷屏 |
| `num` | 分段回复，一条塞 N 个人 | 降低发送条数 |
| `delaytime = 3` 秒 | **聚合窗口** | 攒 3 秒再发，而不是来一个发一条 |
| `is_tx_shield` / `is_rd_shield` | 天选时刻 / 红包期间屏蔽 | **全文最有价值的一行**（见下） |
| `is_open_self` | 是否欢迎自己 | — |

> **天选与红包屏蔽是整个设计的关键。** 抽奖和红包会引发进场洪峰，
> 一个朴素的欢迎机器人会在几秒内试图发出几百条弹幕，账号当场被限流甚至封禁。
> 任何自动发送功能都必须先回答「洪峰来了怎么办」。

**发送侧** —— `SendBarrageThread` + `HttpUserData.httpPostSendBarrage`：

- 单线程 **串行队列**（`barrageString`），不是直接发送
- 每条之间 `Thread.sleep(1455)` —— 刻意避开「1 秒 1 条」的服务端限制
- `maxLength = 20`，超长 **自动分片** 连续发送
- `test_mode` 干跑模式，只打日志不真发

### 1.5 真实约束（从 Danmuji 的错误处理逆推，比文档可靠）

| 返回 | 含义 | 正确处理 |
|---|---|---|
| `code=0` + `message="msg in 1s"` | 触发 1 秒 1 条频率上限 | 回队列重试 |
| `code=0` + `message="msg repeat"` | 内容重复被拒 | 回队列 / 加扰动 |
| `code=0` + `message="f"` 或 `"k"` | 命中屏蔽词 | 丢弃并告知用户 |
| `code=-111` | csrf 失效 | 重新登录 |
| `code=11000` | 含关键字或颜色非法 | 丢弃 |
| 20 字 | 普通用户弹幕长度上限（舰长/大会员更长） | 分片或截断 |

鉴权需要 **SESSDATA + bili_jct**，即主播本人的完整登录态。

### 1.6 风险评估与建议

**建议：不做进场欢迎。** 理由按强度排序：

1. **MagicalDanmaku 的下场是最强的信号。** 这条赛道上功能最全、1242 星的项目，
   作者在 2025-12-25 主动永久归档，声明尊重 B 站知识产权与相关法律法规、规避法律风险，
   并建议用户改用官方客户端。
2. **`msg/send` 不在开放平台里。** 官方开放平台只提供「收」，不提供「发」。
   发弹幕永远是逆向接口，随时可能变，且明确在灰色地带。
3. **风险等级会跃迁。** 我们现在存主播凭据是为了**读**数据，被风控最多是读不到；
   一旦用它**写**，账号就可能被判定为机器人行为。这是两个数量级的差别。
4. **产品定位不匹配。** NovaBot 是数据播报工具，不是场控工具。
   要场控，Bilibili_Danmuji 是现成的、活跃维护的、专门干这个的。

**如果仍然要做**，最小可行且最安全的形态：

- 只对**自己的直播间**，只在**确认开播期间**
- 只做**低频、有明确触发**的：感谢上舰 / SC / 大额礼物。**不做进场欢迎**（进场是高频洪峰）
- 串行队列 + ≥2 秒间隔 + 天选/红包屏蔽 + **每场总量上限**（例如 50 条）
- **默认关闭**，配置项说明里直接写明账号风险
- 必须提供 `test-mode` 干跑
- 单独的开关，不与推送功能耦合——出问题能一键关掉

## 二、开放平台双源整合

### 2.1 两套数据源的能力对比

| | Web 协议（现在用的） | 直播开放平台 |
|---|---|---|
| 入口 | `getDanmuInfo` 取 token → wss 弹幕服务器 | `live-open.biliapi.com/v2/app/{start,heartbeat,end}` |
| 鉴权 | 主播 Cookie（SESSDATA） | `app_id` + `access_key` HMAC-SHA256 签名 + **主播身份码** |
| 合规性 | 逆向接口 | **官方，需项目审核** |
| 用户标识 | **真实 uid** | **`open_id`（每项目独立的假名）** |
| 消息去重 | 无稳定 ID | **`msg_id`** |
| 礼物金额 | `price`，打折礼物不准 | `price` + **`r_price`（实际支付）** |
| 事件覆盖 | 全量，含进场、观看人数、人气值 | DM / GIFT / GUARD / SUPER_CHAT / LIKE / ROOM_ENTER / LIVE_START / LIVE_END |
| 心跳 | 30 秒 | 连接心跳 30 秒 + **项目心跳 20 秒（HTTP）**，断了会话即失效 |
| 稳定性 | 会被风控（412 / -352） | 官方保障 |
| 前置条件 | 扫码登录即可 | **需要注册项目、过审，且主播提供身份码** |

### 2.2 硬约束：`open_id ≠ uid`

开放平台给的是**每个项目独立的假名 ID**。只有主播自己的 `AnchorInfo` 同时给出 `uid` 和 `open_id`；
观众一律只有 `open_id`。

**因此：**

| 能做 | 不能做 |
|---|---|
| 校准聚合量（总弹幕数、总营收、人次、时长） | 合并「我的数据」——同一观众在两源里是两个人 |
| 用 `msg_id` 去重 | 合并排行榜 |
| 用 `r_price` 修正营收精度 | 跨源的账号绑定关系 |
| 开播/下播的第二判据 | — |

### 2.3 设计方案：主从 + 分层，而不是「两源合一」

**Web 源为主。** 绑定、排行榜、「我的数据」全部依赖真实 uid，这是 NovaBot 相对同类项目的核心差异化，不能丢。

**开放平台为副，承担三件事：**

1. **接续** —— Web 源断开（风控 / Cookie 失效 / 长连接静默）时，开放平台顶上，场次不中断。
   这正是「任意一端掉线能接续任务」的落点。
2. **校准** —— 下播时用 `r_price` 修正营收；用 `msg_id` 做跨源去重。
3. **第二判据** —— `LIVE_START` / `LIVE_END` 与 Web 源交叉验证开播下播。

### 2.4 关键设计：场次必须独立于连接

**现在的模型**：一条 WS 连接 ≈ 一个场次。断了就重连，场次靠事件划分。

**新模型**：**场次是独立实体，两个源各自往同一个场次投递事件。**

- 事件按 `(源, msg_id / 序号)` 去重
- **每个指标记录「哪个源贡献、覆盖了哪段时间」**
- 报告里对**有缺口的指标明确标注**，而不是给出一个看起来完整的假数

> 这一条与项目既有原则一致：**一个看似合理的错数比没有数更糟**。
> 接续必须记录缺口，绝不能假装无缝——否则报告会在主播最需要准确的时候悄悄骗人。

### 2.5 分期

| 阶段 | 内容 | 判据 |
|---|---|---|
| 5.0-A | 开放平台**纯旁路只读**接入，不参与报告；双源差异写日志 | 跑满一个月，拿到真实偏差数据 |
| 5.0-B | 接续：Web 断 → 开放平台顶，场次带缺口标记 | 人为断开 Web 源，场次数据连续且缺口正确标注 |
| 5.0-C | 校准：用 `r_price` 修正营收，`msg_id` 去重 | 与 5.0-A 采集的偏差数据对得上 |

**前置条件（需要你操作）**：在开放平台注册项目并过审，拿到 `app_id` / `access_key`；
主播需提供身份码。这一步我做不了。

## 三、从 31 个仓库里挑出来的高价值项

### A. 现在就该补（高价值 / 低成本）

**A1. 「主动下播」与「被切流」必须分开** ★最高优先级
[webhookGo](https://github.com/Janet-Baker/webhookGo) 专门做了这件事：收到下播事件后回查直播间封禁状态。
我们现在一律按主动下播处理——主播看到一场时长异常短的报告会一头雾水，而这是**数据正确性问题**。

**A2. 场次内记录标题变化**
[BilibiliLiveRecordDownLoader](https://github.com/HMBSbige/BilibiliLiveRecordDownLoader) 有这个字段。
一场直播改了几次标题、什么时候改的，是真实的运营信息。
**注意**：`BilibiliEventParser` 目前只解析 7 个 cmd
（`LIVE` / `PREPARING` / `DANMU_MSG` / `INTERACT_WORD` / `SEND_GIFT` / `SUPER_CHAT_MESSAGE` / `USER_TOAST_MSG`），
`ROOM_CHANGE` **没有在收**，需要新增一个解析器——成本仍然很低，但不是零。

**A3. 高能片段识别**
[bilive](https://github.com/timerring/bilive) 与 auto-bilibili-recorder 都按弹幕密度找高能区域。
我们**已经有互动曲线的原始数据**（`drawCurves` 按分钟分桶），
加一层「本场最高能的 3 个时刻 + 时间点」几乎零增量成本，
对主播的价值却很高（直接对应切片素材）。

**A4. per-event 的 exec_command 扩展点**
webhookGo 的配置模型是 `Receivers[type / enable / path / events]`，每个事件下挂
`care / notify / have_command / exec_command` 四个独立开关。
我们已有推送目标建模和按目标的版式配置，**缺的是「收到事件时跑一个外部命令」**——
成本极低，但一次性打开了所有我们想不到的用法。

**A5. 非直播期间的数据留档**
[bilibili-notify](https://github.com/Akokk0/bilibili-notify) 的独立端与
[vtb.Cat](https://github.com/114514ns/vtb.Cat) 都会定时记录粉丝量、投稿等。
**我们目前所有数据都是场次内的，两场直播之间什么都不记**——
于是「本周涨粉多少」这种问题答不了，只能答「每场开播时的粉丝数」。
这是 B1 周报的前置：没有连续留档，周报只能是场次的堆叠，给不出趋势。

> **已经有了、不要重复做的**：盲盒盈亏已完整实现——
> `BOX_COUNT` / `BOX_PROFIT` / `BOX_USERS` / `BOX_PROFIT_USERS` 四个指标、
> 盲盒曲线、盲盒排行与盲盒盈亏排行（默认关闭）、报告卡片上的「盲盒 · 盈/亏 ¥X」、
> 以及 `BilibiliRankingCommand` 里的盲盒榜。
> 调研时我一度把它列成待补功能，核对代码后删除。

### B. 中期功能

**B1. 周报 / 月报定时推送**
[bilibili-notify](https://github.com/Akokk0/bilibili-notify) 的独立端有涨粉/投稿/直播活动留档、
对比表、热力图、雷达图，并让 AI 据此写周报推成卡片。
**我们 4.1.0 已经有数据分析页，差的只是「定时把它推出去」**——增量很小。

**B2. AI 直播总结**
bilibili-notify 有；bilive 用大模型生成标题封面。
我们有完整场次数据 + 全量弹幕，出一段自然语言总结是水到渠成。会产生 API 费用。

**B3. 录播工具 webhook 作为事件源**
录播姬（4725 星，事实标准）、DDTV、OneLiveRec 都提供 webhook。
接一个 HTTP 入口，开播判据就从 1 个变成 3 个。
[biliLive-tools](https://github.com/renmu123/biliLive-tools) 的 webhook 适配层同时支持四种来源，可直接参考。

**B4. 多平台源**
[aio-dynamic-push](https://github.com/klxf/aio-dynamic-push) 覆盖 B站/微博/小红书/抖音/斗鱼/虎牙。
NovaBot 已有 `platform` 抽象与 SPI 机制，**加一个平台是插件级工作，不动核心**。

### C. 明确不做

| 不做 | 理由 |
|---|---|
| 挂机 / 签到 / 经验（BiliBiliToolPro 那条线） | 与定位无关，且是纯风控靶子 |
| 录播 | 生态已成熟（录播姬 4725 星），我们做事件消费方即可 |
| 窗口模拟发消息（ButterBot 那种） | 极脆弱，更易触发风控 |
| Kafka + Flink + ES 全链路 | 几百人的直播间，投入产出比不成立 |

## 四、UI 重构评估

### 4.1 现状

| 项 | 数字 |
|---|---|
| `config-ui/index.html` | **单文件 1903 行** |
| 页签（section） | 7 个：总览 / 推送规则 / 机器人 / 哔哩哔哩 / 群与成员 / 数据分析 / 设置 |
| JS 函数 | 55 个，共享一个全局作用域 |
| 构建步骤 | **无**。内联 CSS + 内联 JS，随 jar 走 |
| 前端测试 | **0** |

### 4.2 必须保住的性质

- **零依赖、零构建**——一个 jar 就能跑，这是本项目最值钱的性质之一
- **配置项由编译期元数据生成**——新增配置项界面自动出现，不存在「界面和代码对不上」

### 4.3 真实存在的问题

1. **CSS 全局选择器在持续制造 bug。** 仅最近就踩了两次：
   `.target input{width:...}` 和 `.backups input{width:140px}` 都误伤了 checkbox，
   把 38px 的开关拉成 140px 的灰条。**这类 bug 会一直发生，因为选择器是全局的。**
2. **没有任何前端回归手段。** 柱状图文字被 `preserveAspectRatio="none"` 横向拉伸那次，
   桌面端看不出来，是靠移动端截图才发现的。
3. **配置全部平铺在一个「设置」页**，配置项已上百个。
   应该按「我要做什么」组织，而不是按配置树组织。
4. **再加 2~3 个页签就会到 3000 行。**（双源状态、周报、若干新功能都要加页）

### 4.4 三个方案

| 方案 | 内容 | 成本 | 结论 |
|---|---|---|---|
| A. 不动 | 继续往单文件加 | 0 | 每次改动风险单调上升，不接受 |
| **B. 拆文件 + 保持零构建** | 拆成 `index.html` + 每 section 一个 `.js` + 一个 `.css`，用原生 ES module（`<script type="module">`）。CSS 用 section 前缀类隔离 | **2~3 人天** | **推荐** |
| C. 上框架 | Vue/React + 构建链 | 8~12 人天 + 长期维护 | **不推荐** |

**为什么不推荐 C**：引入 node 工具链、构建产物进 jar、且要和「配置项由元数据自动生成」
这条核心设计重新对齐。为了前端体验把「一个 jar 就能跑」弄没了，不划算。

**方案 B 的额外收益**：拆开之后可以给关键渲染函数加轻量断言测试（纯函数部分，如 `chartHtml`），
把「只能靠人眼看」变成「至少数据映射有测试」。

### 6.3 流程约定（沿用现有做法，已验证有效）

1. 每个阶段独立成版本，`build.sh` 全绿 + 全量测试后才发 tag
2. 涉及数据正确性的改动**必须先在旁路观察，拿到真实偏差再切换**（5.0-A → 5.0-C 就是这个模式）
3. 配置项改动会被 `ConfigurationConsistencyTest` 拦，红了先查是不是真漏了
4. 部署前备份线上 `application.yml`，改名类变更同步更新
5. **真机验证清单**：涉及直播事件的功能，离线测试全绿不等于能用
