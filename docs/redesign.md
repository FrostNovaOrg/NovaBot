# NovaBot 产品重构方案

> 本仓库是 StarBot 的整理与重构版本。文中「本项目」指 NovaBot，
> 「上游」指原 StarBot 各仓库。命名策略见 [§8.4](#84-命名策略)。

> 本文是动手前的整体设计，覆盖产品定位、用户旅程、配置体系、界面架构、代码重构与实施排期。
> 结论先行：**这个项目的底层工程质量远高于它的产品完成度**，重构的重点不是重写内核，
> 而是把「能跑」和「好用」之间那段路铺出来。

> **实施状态**：本方案已全部落地并在真实环境验证，逐项改动见 [CHANGELOG.md](../CHANGELOG.md)。
> 曾经的遗留项「Cookie 自动续期未经真机验证」已在 4.0.0 解决：扫码登录改走 TV 端接口，
> 令牌有效期 180 天、到期前 30 天自动续期，线上已确认生效。
>
> 本文保留原貌作为设计记录，不随实现回填——**它记录的是动手之前怎么想的，不是现在是什么样**。
> 4.1.0 的命令系统、数据统计与运营分析都在本方案范围之外，此处不会提到。
> 想知道现状看[用户手册](user-guide.md)与[架构说明](architecture.md)。

## 0. 这份文档的范围

**在范围内**：产品交互设计、配置体系、界面信息架构、可用性与异常处理体系、代码重构、实施排期。

**不在范围内**：更换技术栈、重写协议层、引入微服务或数据库中间件。理由见 [§10](#10-明确不做的事)。

**约束**：目标运行环境是小内存 Linux VPS（1C1G 量级），所有方案不得显著抬高常驻资源占用。

## 1. 问题的本质

现有实现里，弹幕协议、插件隔离、WBI 签名、图片绘制、配置元数据驱动这些**难的部分做得都不错**。
真正的缺口集中在一条线上：

> **用户从「装好了」到「确认它真的在工作」之间，没有任何反馈。**

这条线断了以后，所有问题都会被放大：

| 现象 | 根因 |
|---|---|
| 配了半天不推送，不知道哪错了 | 无验证手段，四种错误（群号错/token 错/NapCat 没起/机器人不在群）表现完全一样：什么都不发生 |
| 掉登录后动态推送静默停摆 | 无状态复检，无告警 |
| 改坏配置后程序起不来，界面也进不去 | 保存无校验，无安全模式 |
| 不知道系统健康与否 | 状态页只有内存/线程，没有业务健康度 |

所以重构的第一优先级不是加功能，而是**建立反馈闭环**。

### 1.1 配置复杂度的量化

当前 `application.yml` 模板约 50 个配置项。但让一套系统**真正能跑起来**的必填项只有 4 个：

```yaml
one-bot-address          # NapCat 地址
one-bot-http-port        # NapCat HTTP 端口
one-bot-http-token       # NapCat HTTP Token
one-bot-websocket-token  # NapCat WS Token
```

其余 46 项都有可用默认值。**问题不是配置项太多，而是没有区分「必须懂」和「可以不懂」**——
用户面对的是一份 50 行的扁平清单，无法判断哪 4 行决定成败。

### 1.2 概念泄漏

界面上直接暴露了大量实现概念，用户被迫理解程序内部结构：

| 用户看到的 | 实际含义 | 应该叫 |
|---|---|---|
| `org.frostnova.nova.bilibili.handler.BilibiliLiveOnPushHandler` | 开播时用哪个类渲染消息 | **开播通知** |
| `platform` / `sender` | 一个 OneBot 连接的名字 | **机器人账号** |
| `datasource.json` | 推送规则数据 | **推送规则** |
| `type: 1` / `type: 2` | 群聊 / 私聊 | **群聊 / 私聊**（直接给中文） |

全限定类名不应该出现在面向使用者的界面上。它只应存在于「高级模式」，供自定义插件使用。

### 1.3 被默认值埋没的能力

有些能力已经实现了，但默认关闭或无入口，等于不存在：

| 能力 | 现状 |
|---|---|
| OneBot HTTP/WS 健康探测 | `enable-http-detect` / `enable-websocket-detect` 默认 **false** |
| 邮件告警 | 依赖上面两个探测，因此默认不生效 |
| 推送开关（三层 `enabled`） | 字段存在，但只能手改 JSON |
| `logout()` | 实现完整，**零调用点** |
| 待扫码二维码内容 `pendingQrCodeContent` | 已暴露为字段，但只有终端字符画在用 |

这类「做了但没接上」的成本最低，收益最直接，应优先处理。

## 2. 产品定位与设计原则

### 定位

**给个人和小型社群用的、能自己看住的哔哩哔哩开播/动态通知机器人。**

三个关键词决定了后续所有取舍：

- **个人/小型社群** —— 使用者不一定是开发者。不能要求用户理解 Java 包名、YAML 缩进、OneBot 协议
- **自己看住** —— 部署在自己的 VPS 上，出了问题得能自己查明白，不能只丢一句「推送失败」
- **通知机器人** —— 核心价值是「该响的时候响，不该响的时候别响」。可靠性 > 功能丰富度

### 设计原则

1. **每一步都要有反馈**
   配置完能立刻验证，不必等真实事件发生。这是本次重构的第一原则。

2. **默认值必须是可用的**
   用户不改任何配置也应该能跑。凡是「不改就不工作」的配置项，要么给出合理默认，要么在引导流程里强制填写。

3. **不暴露实现概念**
   类名、协议字段、内部结构都不该出现在主界面。

4. **失败要能自愈或至少能自救**
   程序起不来时，配置界面必须还活着。这是远程部署的生命线。

5. **配置项分层，不平铺**
   必填 / 常用 / 高级三层，默认只展示第一层。

6. **不为小概率场景增加常驻开销**
   VPS 上每一兆内存都算数。新增能力优先做成按需启用。

## 3. 重新设计的用户旅程

### 3.1 现状旅程与断点

```
安装 → [翻日志找 URL] → [翻日志找二维码] → 扫码
     → [手写 JSON，含全限定类名] → 保存
     → [等 UP 主开播] → 没反应 → [翻日志排障] → ???
```

方括号是卡点，共 5 处。

### 3.2 目标旅程

```
安装 → 浏览器自动打开引导页
     → ① 连接机器人（填 NapCat 信息 → 立即测试连通性）
     → ② 登录哔哩哔哩（页面内显示二维码 → 扫完自动进入下一步）
     → ③ 添加第一个主播（输 uid 或空间链接 → 显示昵称头像确认 → 勾选要推的事件 → 选目标群）
     → ④ 发送测试消息（群里真的收到一条 → 完成）
```

**每一步都有即时验证，不通过不让进入下一步。** 走完四步，用户已经确知系统可用，
而不是「配完了，但愿它能работать」。

### 3.3 引导流程的设计要点

| 步骤 | 验证方式 | 失败时给什么 |
|---|---|---|
| ① 连接机器人 | 调 NapCat 的 `get_login_info` | 区分「连不上」「token 错」「端口不对」，各给具体修复建议 |
| ② 登录哔哩哔哩 | 轮询扫码结果 | 二维码过期自动刷新，不用用户操作 |
| ③ 添加主播 | 调接口拉昵称/头像/直播间号 | uid 不存在时明确提示，不是静默失败 |
| ④ 测试消息 | 真的发一条到目标群 | 展示 OneBot 原始返回；机器人不在群里等错误直接可见 |

引导完成后写入配置并标记 `setup-completed`，后续启动直接进主界面。
保留「重新运行引导」入口。

## 4. 配置体系重构

### 4.1 保留双文件划分

现有的 `application.yml`（系统配置）+ `datasource.json`（推送规则）划分是**正确的**：
前者是系统级设置，后者是业务数据，生命周期和变更频率都不同。保留。

要改的是**编辑入口和校验**，不是文件结构。

### 4.2 配置分层

把约 50 项配置重新归类，界面按层展示：

**第一层 · 必填（引导流程中完成，约 4 项）**

机器人连接信息。没有它们系统无法工作。

**第二层 · 常用（主界面直接可见，约 12 项）**

| 配置 | 为什么常用 |
|---|---|
| 静音时段 | **新增**，见 §4.4 |
| 全局推送开关 | **新增** |
| 消息发送间隔 | 防刷屏 |
| 动态检查间隔 | 时效性 vs 请求频率 |
| 备用直播推送开关与间隔 | 被风控时的兜底 |
| 是否自动关注 UP 主 | 会修改用户账号，必须显式可见 |
| 历史动态补推阈值 | 首次启动行为 |
| 配置界面访问控制 | 安全 |

**第三层 · 高级（折叠，其余全部）**

线程池、超时、重试、风控检测参数、调试日志、绘图选项。

> 分层信息作为元数据挂在配置类上（例如自定义注解 `@ConfigLevel(BASIC/COMMON/ADVANCED)`），
> 由既有的编译期元数据管线一并产出，界面读取后自动分层。
> **不引入手工维护的分层清单**，否则又会出现「代码改了界面没改」的老问题。

### 4.3 概念改名

界面文案统一替换（仅 UI 层，不改代码标识符与配置键，避免破坏兼容性）：

- `handler` 全限定类名 → 「开播通知 / 下播通知 / 动态通知」勾选项
- `sender` / `platform` → 「机器人账号」
- `datasource.json` → 「推送规则」
- `type: 1/2` → 「群聊 / 私聊」

后端新增 `/api/handlers`，列出**已注册**的推送处理器及其显示名与适用占位符。
前端据此渲染勾选项——这样插件新增 handler 时界面自动出现，不需要前端硬编码。

### 4.4 新增：静音时段与全局开关

这是通知类产品的刚需，也是被投诉最多的点。

```yaml
novabot:
  core:
    push:
      enabled: true              # 全局推送开关
      quiet-hours:
        enabled: false
        start: "23:00"
        end: "08:00"
        # 静音期间的行为：discard 丢弃 / queue 攒着到期后发
        strategy: discard
```

`queue` 策略需要配合 §7.3 的有界队列，避免静音时段攒爆内存。

### 4.5 保存校验（关键）

当前 `/api/raw` 保存 `application.yml` **零校验**，连 YAML 能否解析都不检查。
这是最严重的可用性陷阱：远程 VPS 上写坏一个缩进，下次重启程序起不来，
**配置界面跟着一起挂**，等于把自己锁在门外。

三级校验：

| 级别 | 检查 | 不通过时 |
|---|---|---|
| 一 | YAML 能否解析 | 拒绝保存，指出出错行号 |
| 二 | 能否绑定到 Properties 类（类型、范围） | 拒绝保存，指出字段与期望类型 |
| 三 | 语义校验（见下） | 拒绝保存，逐条说明 |

`datasource.json` 的语义校验：
- `handler` 类是否已注册
- `platform` 是否对应已配置的机器人账号
- `type` 是否合法、`num` 是否为数字
- `uid` 是否重复

### 4.6 备份与回滚

当前 `.bak` 每次保存都覆盖，只有一层。改为保留最近 10 份带时间戳的备份，
界面提供版本列表与「回滚到此版本」。

## 5. 界面信息架构

### 5.1 页签重组

现有四个页签（常规配置 / 推送配置 / 配置文件 / 运行状态）是**按数据存储方式**划分的，
不是按用户任务。重组为：

| 页签 | 用户任务 | 内容 |
|---|---|---|
| **总览** | 「系统现在好不好？」 | 健康看板、最近推送、快捷操作 |
| **推送规则** | 「我要推谁、推到哪」 | 主播卡片列表、事件勾选、目标管理、模板编辑 |
| **机器人** | 「QQ 侧连接对不对」 | 机器人账号管理、连通性测试、发送测试消息 |
| **哔哩哔哩** | 「B 站账号还好吗」 | 登录状态、扫码登录、退出登录、直播间连接状态 |
| **设置** | 「调参数」 | 分层配置（必填/常用/高级）+ 原始文件编辑（高级模式内） |

原始 YAML 编辑不再是独立页签，收进「设置 → 高级 → 直接编辑配置文件」，
并加醒目提示与三级校验。

### 5.2 总览页设计

这是重构后用户最常看的页面，要在一屏内回答「系统好不好」：

```
┌─ 健康状态 ────────────────────────────────────┐
│  ● 哔哩哔哩登录      正常（uid ×××××××××）      │
│  ● 机器人 qq-onebot  HTTP 正常 / WS 正常        │
│  ● 直播间连接        3/3 已连接                 │
│  ● 最近推送          2 分钟前，成功             │
│  ○ 消息队列          0 条积压                   │
└───────────────────────────────────────────────┘

┌─ 最近推送 ──────────────────────────────────┐
│  16:42  测试主播乙  开播   → 群 12345  成功  │
│  14:03  测试主播乙  动态   → 群 12345  成功  │
│  09:15  某某某        开播   → 群 67890  失败  │
│         └ 机器人不在该群                       │
└───────────────────────────────────────────────┘

[ 发送测试消息 ]  [ 暂停所有推送 ]  [ 运行自检 ]
```

任何一项异常时，卡片变色并给出**具体的修复建议**，而不只是「异常」二字。

### 5.3 推送规则页设计

替代现有的裸 JSON 文本框：

```
┌─ 测试主播乙 ─────────────────────── [开] ─┐
│  uid ××××××××× · 直播间 7000001               │
│                                               │
│  推送事件   ☑ 开播  ☑ 下播  ☑ 动态           │
│  推送目标   群 12345  [编辑模板] [删除]        │
│             + 添加目标                         │
└───────────────────────────────────────────────┘

[ + 添加主播 ]                    [ 高级：编辑原始 JSON ]
```

添加主播时输入 uid 或空间链接，立即拉取昵称/头像/直播间号供确认——
避免「uid 打错一位，配了个陌生人」。

### 5.4 模板编辑器

占位符做成可点击插入的标签，右侧实时预览（用假数据渲染）。
动态推送要能预览绘制出的图片——这块目前完全是黑盒，用户配完只能等真动态。

## 6. 架构与代码重构

### 6.1 生命周期治理

当前全项目**零个** `@PreDestroy` / `DisposableBean`，四个手工创建的线程池停机时不关闭：

| 位置 | 线程池 |
|---|---|
| `JsonDataSource` | `executor` + `scheduler`（文件监听） |
| `NovaMessageSender` | `executor` |
| `DefaultLiveDataService` | `scheduler` |

**改动**：全部收归 Spring 托管，或补 `@PreDestroy` 显式关闭；停机时按序
「停止接收新消息 → 尽力发完队列中已有消息（带超时）→ 关闭长连接 → 关闭线程池」。

另有一处**已实测**的停机阻塞：扫码登录轮询循环跑在 `bilibiliTaskScheduler` 上不响应中断，
Spring 等满 30 秒超时。实测 SIGTERM 到退出 **30.9s / 31.0s**（两次测量）。
首次部署尚未扫码时必然命中。

### 6.2 健康探针体系

定义统一的探针接口，各模块实现并注册：

```java
public interface HealthProbe {
    String name();
    HealthStatus check();   // OK / DEGRADED / DOWN + 原因 + 修复建议
}
```

首批探针：哔哩哔哩登录态、每个机器人账号的 HTTP/WS 连通性、直播间连接状态、
最近推送时间、消息队列积压。

统一供给三个消费方：总览页看板、`/api/health` 接口（便于外部监控接入）、告警系统。

> 注：不引入 Spring Boot Actuator。对这个体量的项目，自建探针接口更轻，
> 且能直接产出中文的修复建议，而 Actuator 的输出面向运维工具而非终端用户。

### 6.3 告警通道抽象

当前告警只有邮件一个出口，且只接了 OneBot 的两处异常，
更要命的是探测开关 `enable-http-detect` / `enable-websocket-detect` **默认 false**，
所以默认状态下等于没有告警。

**改动**：
1. 抽象 `AlertChannel` 接口，实现邮件、**QQ（复用既有 sender，推给管理员）**、Webhook
2. QQ 通道对本项目用户群远比邮件实用，应作为默认推荐
3. 探针状态变化即触发告警，覆盖登录失效、风控、重连失败、队列积压
4. 探测开关默认改为 **true**（开销极小，关掉的收益不抵风险）
5. 同一问题做告警收敛，避免刷屏

### 6.4 安全模式

配置解析失败时，当前行为是整个进程起不来。改为：

```
配置解析失败
  → 不加载业务模块
  → 仅启动配置界面（用内置默认配置）
  → 界面顶部醒目展示解析错误与出错位置
  → 用户改完保存（走三级校验）→ 提示重启
```

这是远程部署的生命线，优先级仅次于停机修复。

### 6.5 消息链路加固

| 问题 | 改法 |
|---|---|
| `LinkedBlockingQueue` 无界，NapCat 掉线时无限堆积致 OOM | 设容量上限，满时丢最旧并计数告警 |
| 发送失败无重试，网络抖动即掉一条推送 | 有限次指数退避重试 |
| `result.getInteger("code")` 自动拆箱，响应缺字段即 NPE | 显式判空 |
| 停机时队列内消息直接丢 | 见 §6.1 的停机序列 |

### 6.6 插件依赖下载加固

> **已作废（2026-09）**：自动下载与退码 90 重启已整段删除；插件依赖改由构建期按 dependency.json 打进 plugins-lib 随包分发，运行期不再联网取 jar。本节保留作设计存档。

`auto-download-dependency` **默认开启**，会下载 jar 落盘并在下次启动加载进 JVM。

| 问题 | 改法 |
|---|---|
| 下载后无任何完整性校验（无 SHA-1 比对、无验签） | 下载 Maven 提供的 `.sha1` 伴生文件并比对 |
| 坐标来自插件内 `dependency.json`（第三方可控），`artifactId` 含 `../` 可写出目录外 | Maven 坐标字符白名单 + 校验 resolve 后路径仍在 `plugins-lib` 内 |
| 重启命令 `cmdLine.split(" ")`，路径含空格即切错 | 改用 `List<String>` 传参，不做字符串拼接再切分 |
| `Files.write` 直接写目标路径，中途失败留下损坏 jar | 写临时文件后原子改名 |
| 派生子进程再 `waitFor`，父 JVM 全程驻留，systemd 下进程树不对 | 以约定退出码退出，交给 systemd 的 `Restart` 策略拉起 |

### 6.7 登录态治理

| 问题 | 改法 |
|---|---|
| `loggedIn` 只在启动时赋值，`logout()` 零调用点，进程永远认为自己已登录 | 定期复检，失效时置回并告警 |
| 动态轮询失败只 `log.debug`，默认级别不可见 | 区分「网络抖动」与「未登录」，后者升 WARN 并触发告警 |
| 无 cookie 续期，SESSDATA 到期必须人工重扫 | 实现官方续期流程（`cookie/info` → `correspondPath` → `refresh_cookie` → `confirm/refresh`） |

> 影响面澄清：直播长连接握手 `uid` 写死 `0`（匿名），备用轮询走公开接口，
> **二者都不依赖登录态**。掉登录只影响动态推送与自动关注。

### 6.8 状态上报修正

`/api/status` 用 `Thread.activeCount()`，该 API 只统计当前线程组及其子组。
**实测界面显示 15，JVM 实际 32**。改用 `ManagementFactory.getThreadMXBean().getThreadCount()`。

## 8. 品牌与资产合规

### 8.1 现状

AGPL-3.0 覆盖的是**代码**。图形资产是独立的著作权客体，字标还额外涉及商标属性——
原作者以 AGPL 开源代码，**不等于**授权他人把其品牌标识用于自己的衍生产品。

`core/nova-core/src/main/resources/logo.png`（600×195）是带 "StarBot" 字样的原创字标设计。
关键在于它不是躺在仓库里的静态文件：`draw-logo` 默认 `true`，该 logo 会绘制在
**每一张推送出去的动态图片底部**，随推送持续对外分发。

同时仓库已改名 NovaBot，却在对外图片上打 StarBot 字标，品牌上也说不通。
源码目录已按核心／插件分层。

### 8.2 处置

| 资产 | 处置 |
|---|---|
| `logo.png` | 移除。重新设计 NovaBot 自有标识，或做纯文字标以规避设计版权 |
| `fonts/font.ttf` | **保留**。阿里巴巴普惠体可免费商用，但需在 NOTICE 保留字体厂商版权声明 |
| 其余资产与文案 | 全仓库排查是否夹带原项目品牌 |

`BilibiliDynamicPainter` 中 `logo()` 返回 `null` 时已有跳过绘制的降级路径，
因此**替换期间可先置空，不阻塞其他工作**。

顺带把 logo 做成可配置：配置项指向外部图片路径，留空则不绘制。
这样用户可以打自己社群的标，也避免了项目再次绑死某一张图。

## 10. 明确不做的事

| 不做 | 理由 |
|---|---|
| 用 Rust / Go 重写 | 常驻内存的绝大部分来自 JVM 与 Spring 基座，GC 后堆实际使用不足 1 MB，业务对象占比极小。真正吃 CPU 的只有图片绘制，是短促突发负载。跨语言边界的复杂度换不回那几十兆 |
| GraalVM 原生镜像 | 本项目插件机制基于运行期类加载，适配工作量大且产物与平台绑定。留作长期选项 |
| 引入数据库作为存储 | 推送规则是低频小数据，JSON 文件足够。上游留下的 MySQL 数据源已移除——它启动时读一次、运行期一条 SQL 不发、没有写回路径，配置界面也只认 JSON，却要拖着 32 MB 的 JPA 依赖。数据源仍是可扩展点，需要的人可用插件自带实现 |
| 引入 Actuator / Prometheus | 体量不匹配。自建探针更轻，且能直接产出面向终端用户的中文修复建议 |
| 前端框架化（React/Vue） | 当前 332 行自包含 HTML 无构建步骤、无外部依赖，符合「单 jar 部署」的定位。表单化后预计增至 1000 行量级，仍在可维护范围 |
| 多实例/高可用 | 个人与小型社群场景，单实例足够 |

## 11. 风险

| 风险 | 应对 |
|---|---|
| 阶段三工作量偏大，可能拖长 | 引导向导与页签重组可拆分独立交付，先上向导 |
| cookie 续期流程涉及 RSA-OAEP 与页面解析，上游接口可能变动 | 失败时降级为告警 + 等人工扫码，绝不能把已有可用凭据弄丢 |
| 表单化后仍需支持自定义插件的 handler | 保留「高级：编辑原始 JSON」入口，两种模式共存 |
| 新增探针与历史缓冲抬高内存 | 历史用固定容量环形缓冲；探针复用既有调度器，不新建线程池 |
| 静音时段 `queue` 策略可能攒爆内存 | 必须依赖有界队列（阶段四 #18），故该策略在阶段四完成前不开放 |
| 新 logo 设计需要时间，可能拖住阶段一 | 拆成两步：阶段一只做「移除 + 置空 + NOTICE 补充」，新标设计放阶段三，两者互不阻塞 |
