# 用户手册

NovaBot 监听哔哩哔哩 UP 主的开播、下播与动态更新，通过 OneBot 协议把消息推送到 QQ 群或好友。

出问题时请看[排障与 FAQ](troubleshooting.md)。

## 0. 适用范围与边界

**先看这一节，它决定这个程序适不适合你要做的事。**

NovaBot 面向**中小型公会、个人势主播及其运营人员**，用于**自有或已获授权**的直播间数据采集、
通知与运营分析。典型规模是**一到十几个直播间**——生产环境的实测规模是 3 个主播 / 3 个直播间。

**本程序不做风控对抗。** 不伪造浏览器指纹、不伪造观看行为数据、不实现针对平台反自动化机制的
对抗手段。这是设计选择，不是能力不足。带来的直接后果是：

- 在**大规模采集场景下不保证账号安全，也不保证数据完整性**，触发平台限流或风控的后果由你承担
- 连接行为按「礼貌客户端」设计：指数退避、全局连接节流、不高频轮询、遵守平台的限流反馈。
  **任何「提高采集速度或密度」的想法都要先过这条线**——历史上唯一一次被限流，
  原因就是我们自己五秒内重连了二十几次

我们**强烈不建议**把它用于非法或未经授权的大规模监控与爬取。项目采用 AGPL-3.0 开源，
我们在技术上无法阻止此类使用；说清立场是为了让你知道它不在支持范围内。
完整表述见 [SECURITY.md](../SECURITY.md)。

## 1. 它需要哪些东西

```
哔哩哔哩  ──拉取──▶  NovaBot  ──HTTP──▶  OneBot 实现  ──▶  QQ 群 / 好友
（一个账号）        （本程序）        （NapCat 等）
```

| 你需要准备 | 说明 |
|---|---|
| 一台能长期开机的机器 | Linux / macOS / Windows 均可。**内存备到 1 GB 以上**，512 MB 不够用，实测见[性能实测](performance.md) |
| Java 17 或更高版本 | 一键安装脚本会自动装 |
| 一个 OneBot 实现 | 推荐 [NapCat](https://github.com/NapNeko/NapCatQQ)，它负责真正登录 QQ 并收发消息 |
| 一个哔哩哔哩账号 | **建议用小号**。用于读取动态流，原因见 [SECURITY.md](../SECURITY.md) |

NovaBot 自己不登录 QQ，只是把消息交给 OneBot 实现去发。所以先把 NapCat 跑起来并登录好 QQ，
再装 NovaBot。

**哔哩哔哩账号建议一定登录，即使你只推直播。**

开播与下播的判断确实是公开信息，不登录也拿得到；但**直播间里的弹幕、礼物这些事件，
未登录时会被平台大幅削减**。2026-08-07 的对照实验：同一个房间、同一时段、两条连接，
登录那条对独立基准的到达率 **100%**，未登录那条只有 **4.3%**——29.3 分钟里只收到 6 条弹幕。
**被削的不只是弹幕**：同一次实验里进房、排行、点赞这些环境消息也只有 **5.4%**（133 / 2479），
与弹幕削得一样多，2026-08-10 的成对复测同样如此（逐类 10~13%）。
也就是说未登录时**整条数据流按比例变薄**，而不是某一类消息单独受影响。

**削减的形状是「有数据但少得多」，不是「报错」**：程序照常运行、日志干净、
下播报告照出，只是数字系统性偏低，你不去比对就发现不了。
未登录时还会**拿不到发弹幕的人是谁**（弹幕里 uid 一律为 0、昵称只留首字，形如 `b***`），
「我的数据」「排行榜」这类按人统计的功能会全部失效。

削减程度还与房间有关：同批实验里另一个房间的未登录连接到达率有 99.7%。
**这意味着你不能拿「我这里看着正常」当作依据**。

## 2. 安装

### Linux 一键安装

```bash
./install.sh
```

脚本会依次完成：检查并安装 Java 17、构建、安装到 `/opt/starbot`、生成配置、创建 systemd 服务。

可选参数：

| 参数 | 作用 |
|---|---|
| `--dir /srv/novabot` | 指定安装目录（默认 `/opt/starbot`） |
| `--port 7827` | 指定服务端口 |
| `--no-service` | 跳过 systemd 服务创建 |

启动并看日志：

```bash
sudo systemctl start starbot && sudo journalctl -u starbot -f
```

### 手动安装

```bash
./build.sh
```

产物在 `dist/build/`，把整个目录拷到目标机器，然后：

```bash
./start.sh
```

> 构建必须走 `build.sh` 而不是直接 `mvn package`，原因见[架构说明](architecture.md#10-构建)。

### 容器部署

```bash
./build.sh
docker build -f dist/templates/Dockerfile -t starbot:4.1.0 dist/build
docker run -d --name starbot --restart unless-stopped \
  -v starbot-data:/app -p 127.0.0.1:7827:7827 starbot:4.1.0
```

**卷必须挂在 `/app`。** 配置、登录凭据、推送规则、插件依赖全都写在工作目录下，
挂到 `/app/data` 之类的子目录等于什么都没持久化，容器一重建就得重新扫码。

升级换新镜像即可，卷里的配置与登录态会保留。其余说明见
[dist/templates/Dockerfile](../dist/templates/Dockerfile) 顶部的注释。

## 3. 首次配置

启动日志里有两样东西：

1. **配置界面地址**，形如 `http://127.0.0.1:7827/config?token=xxxx`
2. **登录二维码**（终端字符画）

用浏览器打开前者。界面默认只监听本机回环地址，**如果 NovaBot 装在远程服务器上**，
先在自己的电脑上建隧道：

```bash
ssh -L 7827:127.0.0.1:7827 用户名@服务器地址
```

然后在本机浏览器打开同一个地址。

打开后总览页顶部就是**首次配置向导**，四步，每步都会当场验证：

| 步骤 | 做什么 | 怎么算过 |
|---|---|---|
| 1 连接机器人 | 填 NapCat 的地址、端口、Token | 点「测试连接」显示实现版本与登录的 QQ 号 |
| 2 登录哔哩哔哩 | 用手机客户端扫二维码 | 页面自动变为「已登录」并显示 uid |
| 3 添加主播 | 输入 uid 或粘贴个人空间链接 | 页面显示已配置的主播数 |
| 4 发送测试消息 | 在「机器人」页发一条真消息 | 群里真的收到 |

四步都完成后向导会自动收起，之后随时可以展开重新检查。

**第 4 步不能跳过。** 群号写错、Token 不匹配、机器人不在群里——这几种错误的表现完全一样：
什么都不发生。发一条真消息是唯一能当场分辨的办法。

### 不想登录：匿名模式

只要直播弹幕、礼物这些数据，不需要动态推送，也不想为采集绑一个账号的话，
可以免登录跑：

```yaml
starbot:
  bilibili:
    account:
      anonymous: true
```

开启后**完全不使用凭据**：不读已保存的凭据、不弹二维码、不做登录态复检与续期。
直播采集照常，[事件输出](#事件输出)照常。首次配置向导的第 2 步会自动标记为已定，不再催你扫码。

**但它拿到的数据是不完整的，这是实测结论而不是推测：**

| 差异 | 实测 |
|---|---|
| 弹幕会不会少 | **会。** 部分房间的弹幕被服务端限制下发，同一房间同一时段，匿名连接的到达率实测低至 **4.3%**（登录态同时段 100%） |
| 发送者是谁 | **弹幕拿不到。** uid 被抹成 `0`，昵称只留首字（形如 `b***`）。但**头像和粉丝勋章是真的**，点赞消息也仍带完整 uid 与昵称——抹除是按消息类型来的，不是整条连接一刀切 |
| 动态推送、自动关注 | **不可用**，它们必须有登录态 |

哪些房间会被限制、按什么规律限制，目前还没有结论——这正是我们在测的事。
所以匿名模式只适合「有多少算多少」的场景（本机试跑、给下游供一路粗粒度事件流），
**不要拿它做任何依赖「数得准」的事**，比如统计弹幕数、算互动率、评估活跃观众数。

程序自己也是这么说的：启动日志和运行状态页里的那句提示，与本节用的是同一份文本。

> 匿名模式：部分房间的弹幕可能被服务端限制下发（实测已证实），拿得到的弹幕里发送者 uid
> 会被抹成 0、昵称只留首字（形如 b\*\*\*）；动态推送与自动关注不可用。需要完整数据请配置登录

要换回登录模式，把 `anonymous` 改回 `false` 重启，扫码即可。

## 4. 界面导览

| 页签 | 回答什么问题 |
|---|---|
| **总览** | 系统现在好不好？健康自检、最近推送、暂停推送、立即自检 |
| **推送规则** | 我要推谁、推到哪、推什么内容 |
| **机器人** | QQ 这一侧连通吗？连接参数、连通性测试、发送测试消息 |
| **哔哩哔哩** | 账号还在线吗？登录状态、扫码登录、退出登录、监听中的直播间 |
| **群与成员** | 群里发生了什么？各群的命令开关、「@我」订阅名单、账号绑定 |
| **数据分析** | 播得怎么样？按周/月看场次、时长与各项互动数据的趋势 |
| **设置** | 调参数。分层展示，原始配置文件编辑收在「高级」里 |

### 推送规则怎么配

不需要手写 JSON：

1. 在输入框填 uid 或直接粘贴个人空间链接（`https://space.bilibili.com/12345678`）
2. 界面会先把**昵称和头像**拉出来让你确认——避免 uid 打错一位却配了个陌生人
3. 确认后卡片出现，勾选「开播 / 下播 / 动态」
4. 添加推送目标：选机器人、选群聊还是私聊、填群号或 QQ 号
5. 点右下角保存

想改推送文案，勾选事件后点「编辑模板」，占位符做成了可点击的标签，右侧实时预览。

> 需要用自定义插件提供的处理器时，用工具栏右侧的「高级：编辑原始 JSON」。

### 只采集不推送的房间

配了主播、但一个推送目标都不加，就是一个**纯监听房间**：程序照常连接直播间、
照常累计数据、照常把事件送进[事件输出](#事件输出)，但**一条 QQ 消息都不发**。
自建面板、只想留数据不想被消息打扰的场景用这个。

**前提是 `only-connect-necessary-rooms` 为 `false`**，这是默认值，不用改。
只有手动把它改成 `true` 时，没有直播推送目标的主播才会被整个跳过——
**表现是「加了主播却什么都没发生」**。这种情况日志里会逐个列出被跳过的房间，
看一眼日志就知道是不是撞上了它。它是[大规模部署下减少连接数的优化项](performance.md#关闭不需要的功能)，
开之前先确认自己没在用纯监听房间。

### 设置页的分层

配置项有几十个，但真正决定系统能不能跑起来的只有几个。界面默认只显示必填与常用项，
勾选「包含高级选项」才展开其余的。**默认不显示的那些通常真的不需要改。**

修改后点保存，改动会逐行写入 `application.yml`，**你原有的注释、顺序、格式都会保留**。
保存前会校验 YAML 语法与字段类型，并自动留一份带时间戳的备份（保留最近 10 份，可在界面回滚）。

**大部分配置项要重启才生效**，「暂停全部推送」是个例外，它立即生效。

### 数据分析页

每场直播下播时，NovaBot 会把这一场追加到 `sessions.jsonl`（主播、开播下播时刻、时长、
全部指标与各计分表人数）。「数据分析」页按**周**或**月**把这些场次聚起来，
可以只看某一位主播。**这些数字只在后台看得到，不会发到群里。**

看之前先知道三件事，否则容易把数字读歪：

- **整场算在开播那一天。** 周日 23:40 开播、周一凌晨 2:10 下播的那场，
  整场都算在周日所在的那一周。否则同一场会在两个周期里各算半截
- **中间没播的周期也会列出来，显示 0 场。** 空着的那一格本身就是信息，
  跳过它会让趋势看起来比实际连贯
- **表里的「人次」不是「人数」。** 归档只存了每场的人数、没存人的名单，
  所以同一个人在三场里都发过弹幕就会被计三次。**周/月的独立人数是算不出来的**，
  界面上写「人次」不是措辞讲究，是这个数确实只能这么解释
- **开播时的粉丝数、粉丝团人数、大航海人数不参与统计。** 它们记的是某一刻的存量，
  把十场的粉丝数加起来既不是月初也不是月末的数字

归档从 4.1.0 起才有，之前的直播没有记录，不会追溯。文件在数据目录下，
每条 300~800 字节（取决于该场产生了多少种指标），可以直接拿去做别的分析。

## 5. 消息模板

| 占位符 | 适用事件 | 含义 |
|---|---|---|
| `{uname}` | 全部 | UP 主昵称 |
| `{title}` | 开播 | 直播间标题 |
| `{cover}` | 开播 | 直播间封面图 |
| `{url}` | 开播、下播、动态 | 跳转链接 |
| `{time}` | 下播 | 本场直播时长 |
| `{action}` | 动态 | 动态动作，如「投稿了视频」 |
| `{picture}` | 动态 | 渲染出的动态图片 |
| `{next}` | 全部 | 消息分条 |
| `{at=all}` | 全部 | @全体成员，仅群聊有效 |

内置处理器与各自可用的占位符：

| 处理器 | 触发时机 | 可用占位符 |
|---|---|---|
| `BilibiliLiveOnPushHandler` | 开播 | `{uname}` `{title}` `{cover}` `{url}` |
| `BilibiliLiveOffPushHandler` | 下播 | `{uname}` `{time}` `{url}` |
| `BilibiliDynamicPushHandler` | 动态更新 | `{uname}` `{action}` `{url}` `{picture}` |

在 `datasource.json` 里它们要写全限定名，前缀是 `com.starlwr.bot.bilibili.handler.`。
用界面配置时不需要接触这些类名。

### 下播报告的版式

下播报告（`BilibiliLiveReportPushHandler`）**按推送目标分别配置**：同一场直播推给不同群时，
可以各自决定展示哪些区块。

**在界面上配最省事**：推送规则页勾上「下播报告」后点「编辑模板」，
模板下方就是这些开关与数字框。只有你改动过的项会写进配置文件，
没碰过的继续跟随默认值。

要手写的话，写在该条推送内容的 `params` 里：

| 选项 | 默认 | 含义 |
|---|---|---|
| `cover` | true | 直播间封面横幅 |
| `cards` | true | 数据卡片栅格 |
| `fans_change` | true | 粉丝 / 粉丝团 / 大航海的本场变化 |
| `interaction_curve` | true | 互动曲线 |
| `guard_list` | true | 本场开通大航海的观众名单 |
| `danmu_cloud` | true | 弹幕词云 |
| `highlights` | true | 高能时刻：弹幕最密集的几个时段 |
| `title_changes` | true | 本场的标题变化，没改过时不占版面 |
| `danmu_ranking` | 5 | 弹幕排行榜取前几名，**0 为不展示** |
| `gift_ranking` | 5 | 礼物排行榜 |
| `super_chat_ranking` | 5 | 醒目留言排行榜 |
| `box_ranking` | 0 | 盲盒数量排行榜 |
| `box_profit_ranking` | 0 | 盲盒盈亏排行榜 |

排行榜类填的是「取前几名」，一个数字同时表达了开关与规模；填负数或超大值会被夹到 0~20，
不会让报告画崩。**为零的区块本来就不展示**，冷清场次的报告会自动收紧，不留空洞。

`fans_change` 每次出报告要额外打三个接口（粉丝数、粉丝团人数、大航海人数），
在意接口频率的话可以关掉它。

互动曲线里的「看过人数」是**本场累计来过多少人，不是同时在线人数**。它只增不减，
所以真正有信息量的是曲线的**斜率**——什么时候在涨人。哔哩哔哩早年那个「人气值」已经废弃
（实测恒为 1），不再采集。

`highlights` 给出的是**距开播多久**，也就是回看录播时要拖到的位置。
它只挑真正的高峰：一个时段既要显著高于本场的常态，本身也要够热闹——
**一场总共二十条弹幕的冷场不会硬凑出三个「高能时刻」**，那一栏干脆不出现。
判据是弹幕密度，不涉及任何金额，因此不随金额可见性降级。

### 别让大群看到收益

上面这些开关回答的是「报告长什么样」，而**「谁能看到金额」是另一个问题**，
不在 `params` 里配——它是**会话的属性**，在「群与成员」页每个会话卡片的顶部。

分开的理由很实在：`直播间数据`、`数据排行榜 礼物` 这些命令谁都能在群里打，
它们不属于任何推送目标，读不到报告的版式配置。只关报告里的金额，一句命令就全漏回来了。

**默认私聊显示、群聊隐藏。** 关掉之后：

| 位置 | 变成 |
|---|---|
| 报告概览行 | 「本场收益 ¥X」整段省略，直播时长保留 |
| 报告数据卡片 | 礼物→「N 人 / 送出礼物」，醒目留言、大航海、盲盒去掉 ¥ 后缀 |
| 报告互动曲线 | **曲线照画**，只是不标峰值——归一化面积图不含绝对值，正是最适合给大群看的氛围 |
| 报告排行榜 | 礼物榜、醒目留言榜、盲盒盈亏榜**整榜不出**；弹幕榜、盲盒个数榜、大航海名单照常 |
| `直播间数据` 等命令 | 同上，卡片改用人数与条数 |
| `数据排行榜 礼物` 等 | 明确回一句「本会话不展示金额相关的榜单」，并列出还能查哪些 |

金额榜整榜不出而不是抹掉数字：那三张榜的每一行本质都是「某人花了多少钱」，
只去掉右侧的数字，仍然是在公开排消费。

于是「大群只放词云和弹幕数、自己私聊看全量」不需要维护两套版式——
同一份版式配置，推给谁就按谁的可见性来。

想在报告底部打自己社群的标，在设置页填 `starbot.bilibili.live.report-logo-path`
（本地图片路径），图片会按固定高度等比缩放，绘制在署名之上。
动态图片的标识是另一项 `starbot.bilibili.dynamic.logo-path`，两者分开配置——
要一致的话填成同一个路径即可。

## 6. 群里能用的命令

**机器人只在已配置推送的群里应答**，其他群发什么它都不会说话；
群里正常聊天时随口说到某个命令名，它也不会回——只有命令名开头的消息才算数。
在群里发 `菜单` 可以看到当前可用的全部命令。

| 命令 | 说明 |
|---|---|
| `菜单` | 列出可用命令，别名 `帮助` `命令` |
| `启用命令 <名称>` / `禁用命令 <名称>` | 按群开关某条命令。`菜单` 与 `启用命令` 不可禁用 |
| `开播@我` / `取消开播@我` / `开播@名单` | 订阅开播提醒时被 @ |
| `动态@我` / `取消动态@我` / `动态@名单` | 订阅动态提醒时被 @ |
| `绑定 <uid>` → `确认绑定` | 关联自己的哔哩哔哩账号，个人数据查询的前提 |
| `解绑` | 解除绑定 |
| `直播报告` | 直播中随时拉一份实时报告图，不必等下播 |
| `我的数据` / `我的总数据` | 自己在该直播间的互动数据与名次 |
| `直播间数据` / `直播间总数据` | 直播间整体数据 |
| `数据排行榜 <榜单> [页码]` | 弹幕 / 礼物 / 醒目留言 / 盲盒 / 盲盒盈亏 / 大航海榜，每页 10 人 |
| `总数据排行榜 <榜单> [页码]` | 同上，但统计历次直播的累计 |

几点说明：

- **本群配置了多位主播时**，命令要带上是哪一位，如 `我的数据 测试主播`
  或 `数据排行榜 礼物 2 3000000000000001`。只配了一位时可以省略
- **带「总」字的命令需要 Redis**。没配时它会明说「需要配置 Redis」，
  而不是回一堆 0 让人误以为数据丢了。在设置页搜 `spring.data.redis.host`
  填上地址即可（**只需本机可达，切勿暴露到公网**），改完重启
- **同一个群 3 秒内只响应一条命令**，防止刷屏
- **`启用命令` / `禁用命令` 只有管理员能用**。群主、群管理员自动有权限；
  机器人的主人未必是每个群的管理员，可在设置页的 `starbot.core.command.admins`
  里填一份跨群生效的超级管理员 QQ 号名单。其余命令（`@我`、`绑定`、`我的数据` 等）
  只影响自己，任何人都能用
- **绑定核对的是 uid 有没有打错，不是账号归属**。没有接口能证明
  QQ 号和哔哩哔哩账号属于同一人，所以第一步会把昵称回给你确认。
  能查到的也只是此人在直播间里的互动量，这些在直播间本就公开可见

### 在界面上查看与收拾

上面这些都是**群成员在聊天里产生的状态**，存在 `state.json`。
控制台的「群与成员」页把它们全都摊开：

- **命令开关**——每个群一张卡片，列出全部命令及其开关。
  群管理员在群里关掉某条命令后机器人就对它一言不发，
  不看这里根本无从得知是「坏了」还是「被关了」。开关改动**立即生效并立刻落盘**，不用点保存
- **「@我」订阅名单**——哪些群、哪些主播下积了多少人，可移除单个人或清空整份名单。
  人退群后订阅仍会留着，@ 一个不在群里的号是无效的
- **账号绑定**——可解绑，但**不提供代人绑定**。绑定本就无法验证归属，
  替别人建立一条对应关系等于凭空造出一份看似可信的证据

两类容易被忽略的东西也会显示出来，而不是悄悄藏起来：

- 从推送配置里删掉、但状态仍残留的群，标为「未配置推送 · 仅残留状态」——
  它的命令还关着，一旦重新配置推送就立刻生效
- 状态文件里禁用了、但当前已无此命令的记录（改过名或已删除），列在「状态文件中的残留」下，可一键清掉

## 7. 常用设置

### 静音时段

半夜被机器人吵醒是这类工具最常见的抱怨。设置页搜「静音」：

```yaml
starbot:
  core:
    push:
      quiet-start: "23:00"
      quiet-end: "08:00"     # 允许跨零点
```

两项任一为空即视为不启用。

### 出问题时通知我

登录失效、连接中断、队列积压默认只写日志。要主动收到通知，配置告警接收方：

```yaml
starbot:
  core:
    alert:
      enabled: true
      qq-platform: qq-onebot   # 填 senders 里的某个 name
      qq-type: 0               # 1 群聊、0 私聊
      qq-num: 你的QQ号
```

> `qq-type` 与推送目标的 `type` 是同一套编码：**1 是群聊，0 是私聊**。填其他数字告警发不出去。

**但只配 QQ 告警有个死角**：告警本身也走机器人的推送链路，QQ 掉线时它跟着一起失效——
而「QQ 掉线」恰恰是最需要知道的那类故障。因此还可以配一路不经过 QQ 的 Webhook，
推到手机上的通知类应用：

```yaml
      webhook-url: https://api.day.app/你的key
      webhook-method: GET
      webhook-title-field: title
      webhook-content-field: body   # 各家的正文字段名不同，填错会推出空消息
```

两路可以同时开。同一个问题在 `convergence-interval`（默认 1 小时）内只告警一次，
避免故障持续时反复刷屏。

**掉线是怎么判定的** — 三个互相独立的判据，任何一个都不依赖群里有没有人说话：

| 判据 | 频率 | 能发现什么 |
|---|---|---|
| Websocket 心跳 | 实现自报，NapCat 默认 30 秒 | 长连接静默失效；QQ 账号掉线（心跳自带 `status.online`） |
| HTTP `get_status` | `http-detect-interval`，默认 300 秒 | OneBot 实现挂了、端口不通、账号掉线 |
| 连接关闭事件 | 即时 | 连接被对端断开 |

心跳连续三次没来才判失效（默认 90 秒，不足 `websocket-silence-timeout` 时按后者），
偶尔一次网络抖动不会误报。**若你的 OneBot 实现关掉了心跳**（NapCat 的 `heartInterval` 设为 0），
静默就不再具备判据意义，程序会在日志里提示一次并停用这条判据，改由 HTTP 检测兜底。

### @全体成员 用超了会怎样

QQ 对 @全体成员 有每日上限，**用超之后平台会静默忽略**：消息照发，但那一下 @ 不生效，
配置的人往往过很久才发现「怎么没人被 @ 到」。

QQ 的额度实测有**两个维度**：

| 维度 | 额度 | 说明 |
|---|---|---|
| **账号** | 10 次/天 | 这个 QQ 号在**所有群之间共用**这 10 次，通常先撞到的是它 |
| **群** | 20 次/天 | 群里所有有权限的人共用，机器人只是其中之一 |

NovaBot 两个维度都记账，任一用尽就把 @ 摘掉、退化为普通消息并记日志——**通知本身照发**：

```yaml
      at-all-daily-limit: 10          # 账号维度，全部会话共享
      at-all-session-daily-limit: 20  # 会话维度，各群独立
```

填 0 表示该维度不限制。

### 被平台警告、切流、封禁时会怎样

**会立刻走告警通道通知你，而不是发到粉丝群里。**

这三件事都需要主播本人马上处理，而粉丝帮不上忙——把「本场被平台切断了」广播给观众，
除了尴尬没有别的作用。所以它们走的是上面配的告警接收方（QQ 私聊 / 邮件 / Webhook），
和登录失效、连接中断是同一个出口。

| 情况 | 说明 |
|---|---|
| 违规警告 | 切流之前的最后一次提醒，处理及时就不会真被切 |
| 直播流被切断 | 本场已被平台掐掉 |
| 直播间被封禁 | 比切流更严重，封禁期间连开播都不行；带解封时间 |

判据来自直播间长连接自己下发的指令，**不需要额外请求任何接口**，也不受风控影响。

被切断或被封禁的场次会在归档里标记出来。这是**数据正确性问题**：一场被掐掉的直播，
时长、营收、互动全都不可比，混进趋势图里看起来就是「这天状态怎么这么差」，
而真实原因是那场根本没播完。

### 直播间标题改了会记下来吗

会。开播时记一次初始标题，此后每次改动各记一条，一并进下播报告与场次归档。
**平台在主播打开设置又原样保存时照样下发通知**，内容没变的不会被记成一次改动。

### 让事件去触发一个脚本

开播时启动录播、上舰时写一行台账、被切流时给自己发条提醒——这类内置功能覆盖不到的用法，
可以挂一个外部程序：

```yaml
starbot:
  core:
    exec:
      enabled: true          # ⚠️ 默认关闭
      timeout: 30            # 单条命令最长执行时间，单位：秒
      max-concurrent: 4      # 同时执行的命令数上限，超出的直接丢弃
      rules:
        - event: LiveOnEvent
          command:
            - /opt/scripts/record.sh
            - "{room_id}"
            - "{uname}"
```

`event` 填事件类名，简名或全限定名都行，**沿继承链匹配**——填 `LiveOnEvent`
就能同时命中各平台的具体开播事件。可用占位符：
`{event}` `{platform}` `{uid}` `{uname}` `{room_id}` `{timestamp}` `{json}`。

> **`command` 是参数数组，不是一整行命令。** 第一项是可执行文件，其余各项各自是一个独立参数。
> 想用管道、重定向之类的 shell 特性，请自己写一个脚本文件再在这里填它的路径。
>
> 这不是写法上的讲究。事件里带的是昵称、弹幕正文这类**完全由陌生人决定**的内容，
> 一旦拼成命令行字符串交给 shell，一个昵称叫 `; rm -rf ~` 的观众就能让你的脚本执行任意命令。
> 走参数数组时，这段文本无论长什么样都只是**一个参数**。

超时会被强制结束；并发超过上限的那次**直接丢弃并记日志**，而不是排队——
等到十分钟后才执行的「开播启动录播」没有任何意义。

### 事件输出

把直播间事件按「事件输出协议 v1」实时推给**本机的其他程序**，用于自建面板、
独立统计这类内置功能覆盖不到的场景。它只输出，不接受任何指令。

> 只是想在自己机器上接一条真实事件流来开发的话，看
> [在本机把真源跑起来](runbook-local-source.md)——零凭据，不用扫码也不用配 QQ 机器人。

```yaml
starbot:
  bilibili:
    event-stream:
      enabled: true               # 默认关闭
      path: /nova/events
      buffer-size: 2000
```

打开后地址是 `ws://127.0.0.1:<server.port>/nova/events`，与配置界面共用端口。
连上后服务端先发一条 `hello`（带会话标识与能力集），随后是实时事件；
每条事件有一个会话内严格递增的 `seq`，断线重连时用 `resume` 就能把缺的那段补回来。

> ⚠️ **只接受来自本机回环地址的连接，且这一点与 `server.address` 无关。**
> 即使你为了对外提供推送接口把监听地址改成了 `0.0.0.0`，事件流也只认本机。
> **需要从其他机器读取请自行建立 SSH 隧道**：
>
> ```bash
> ssh -L 7828:127.0.0.1:7827 你的服务器
> ```
>
> **直接暴露到公网风险自负**——这条流里有观众的昵称、uid 与消费金额。

几条口径上的提醒，连上后 `hello` 里的 `notes` 字段也会重复一遍：

- **点赞未聚合**，每次点赞单独一条、`count` 恒为 1
- **`live_state` 没有中途接入的快照**，只在开播、下播、标题变更时下发
- **`source_state` 的 `disconnected` 只在主播被移出数据源时下发**；房间还在监听列表里时一律是 `reconnecting`
- **房管标志只有弹幕消息带**，其余消息恒为 `false`，含义是「这条消息没说」而不是「不是房管」
- 每条事件附带平台原始报文（`rawJson`），**字段随平台改版而变，不要当契约用**

缓冲是全部房间共用的一条流。房间多或弹幕密时要把 `buffer-size` 调大，
否则客户端重连时会被告知补不上而必须清空重来；每条约数 KB，调大前先掂量内存。

### 机器人不是管理员时会怎样

**会自动摘掉 @全体成员，只发正文。**

这里堵的是 QQ 的一个漏洞：一个在群里只是普通成员、客户端根本点不出 @全体成员 的账号，
**经 OneBot 接口发送却能真的 @ 到全体**。能做不等于该做——绕过权限强行 @ 全体属于滥用，
有招致账号风控的风险，而风控一来整条推送链路都会停摆。

所以想让 @全体成员 真正生效，**请把机器人设为群管理员**；不设也不会出错，只是不带 @。
日志里会明说：「机器人在群 X 中的角色为 member，没有 @全体成员 的权限，相关占位符将被移除」。

### 手动编辑配置文件

`application.yml` 与 `datasource.json` 都可以直接编辑，改完重启即可。
`datasource.json` 的完整示例见发行包里的 `datasource.example.json`。

推送目标的 `type`：**1 为群聊，0 为私聊**，`num` 是对应的群号或 QQ 号。填其他数字会被当作
「未知类型」在运行期丢弃，因此界面在保存时就会拦下。

## 8. 升级

### 从本项目的旧版本升级

用 `install.sh` 或容器部署时下面这些都由脚本处理，手工升级才需要照做：

1. 停止服务
2. **备份 `application.yml`、`datasource.json`、`cookies.json`、`cookies.key`**
3. 用新版本的产物替换 `StarBotCore.jar` 与 `lib/`
4. `plugins/` **不要整个替换**——里面可能有你自己放的第三方插件，覆盖等于把它们卸载。
   只替换内置的那三个插件，并删掉它们的旧版本文件（同一插件留下两个版本会被同时加载）
5. 保留原有的 `application.yml` 与 `datasource.json`
6. 启动，看日志有没有「未知配置项」之类的告警

配置项若有删改，构建时的一致性测试会拦住，因此升级后配置一般可以直接沿用。

### 从上游 StarBot 3.0-beta8 迁移

**必须改一处**：`datasource.json` 中推送内容的指定方式变了。

```jsonc
// beta8 二进制版：按事件类名
{ "event": "com.starlwr.bot.bilibili.event.live.BilibiliLiveOnEvent" }

// 本项目（跟随上游公开源码）：按处理器类名
{ "handler": "com.starlwr.bot.bilibili.handler.BilibiliLiveOnPushHandler" }
```

其余配置键名保持兼容，`cookies.json` 也可直接沿用（首次启动会自动迁移为加密存储）。

### 凭据会不会掉

**一般不会。** 扫码登录走的是电视端接口，拿到的令牌有效期 180 天，
到期前 30 天程序会自动续期（`starbot.bilibili.account.auto-refresh-cookie`，默认开启）。

启动日志会明说拿到的是哪一种凭据，出问题先看这一行：

- **「已取得可自动续期的登录令牌, 有效期至 X」** — 正常，不用管
- **「已取得网页端刷新口令」或「未取得任何刷新口令」** — 退化了，重新扫一次码即可

> 退化的成因是个已知限制：网页端扫码登录时，服务端会把「持久化刷新口令」返回为空
> （同一账号在浏览器里登录则拿得到）。补齐请求参数、设备标识与 User-Agent 后仍为空，
> 因此改走了电视端接口。拿不到口令时续期会直接跳过，不会有副作用，只是没法自动续。

掉登录的表现是动态推送静默停止（直播推送不受影响），健康自检会明确告警，重新扫码即可。

## 9. 安全须知

- 配置界面**默认只监听本机回环地址**并要求访问令牌。要从外网访问，请走 SSH 隧道，
  不要直接把端口暴露到公网
- 推送接口有 Token 鉴权与来源 IP 白名单，默认只放行本机
- `cookies.json` 等同于哔哩哔哩账号的完整控制权，默认加密存储，密钥在 `cookies.key`。
  **两个文件都要妥善保管，也都不要提交到任何仓库**
- `starbot.core.exec` 能执行任意程序，**默认关闭**。打开前请确认清楚要跑的是什么；
  命令以参数数组执行而非交给 shell，因此昵称、弹幕内容无法逃逸成命令
- 详见 [SECURITY.md](../SECURITY.md)

## 10. 资源占用

空载实测常驻内存 105–110 MB；**带负载**（4.1.0，监听 2 位主播、直播间长连接与 OneBot 双通道
均已建立、Redis 已启用）实测约 476 MB——**按后者规划机器内存**，512 MB 的机器不够用。

这个量级随**主播数**与**功能开启情况**变化明显，照抄任何一个数字都不可靠，上线后自己测一次才算数。
1 GB 的机器要把 `-Xmx` 与 systemd 的 `MemoryHigh` / `MemoryMax` **一起**往下调，
只压其中一个会让进程在堆涨起来时被内核直接杀掉。
完整实测数据、测量条件与容量建议见[性能实测](performance.md)。
