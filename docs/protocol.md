# 事件源协议

**版本 2 · 冻结于 2026-09-03**

> 🔴 **改协议须抬版本号并同步本件。** 本件与代码同仓、随代码走，
> 下游（面板、独立统计、自建消费者）以本件为准。

WebSocket，UTF-8 JSON，一帧一条消息。

本协议是数据源与消费方之间唯一的边界。它按「源无关」设计——当前实现走 NovaBot，
但任何能产出这些消息的进程都可以充当数据源；反过来，任何能读懂本件的程序都可以充当消费方。

**真源是本仓的代码**，具体是：

| 东西 | 在哪 |
|---|---|
| 版本号、`hello`、心跳、认证、回补窗口 | `novacore/src/main/java/com/starlwr/bot/core/protocol/NovaEventEndpoint.java` |
| 序号、环形缓冲、分发 | 同目录 `NovaEventStream.java` |
| 握手守卫（回环、拒收凭据） | 同目录 `NovaEventStreamConfiguration.java`、`NoCredentialsInHandshake.java` |
| 每种消息的字段 | `starbot-bilibili/src/main/java/com/starlwr/bot/bilibili/protocol/NovaEventMapper.java` |
| 可执行的校验器 | `novacore/src/test/java/com/starlwr/bot/core/protocol/NovaProtocolSchema.java` |

校验器随协议留在核心，并以 `test-jar` 供各平台插件的测试引用——
各平台的映射器产出的信封要按同一把尺量，一个平台抄一份就等于多一个会和协议漂开的副本。
拿实抓报文回放这把尺的流程见[《拿实抓语料回放协议校验》](runbook-protocol-corpus.md)。

面向使用者的开关与运维说明在[《使用指南》的「事件输出」一节](user-guide.md)，本件只写线上形状。

## 1. 传输与端点

| 项 | 值 |
|---|---|
| 地址 | `ws://127.0.0.1:<server.port>/nova/events` |
| 路径配置键 | `starbot.core.event-stream.path`，默认 `/nova/events` |
| 开关 | `starbot.core.event-stream.enabled`，**默认关闭** |
| 回补缓冲条数 | `starbot.core.event-stream.buffer-size`，默认 `2000` |
| 是否要求口令 | `starbot.core.event-stream.require-token`，默认 `false` |

旧配置键前缀 `starbot.bilibili.event-stream` 仍然认得，**逐项**被新键压过：
新键没写到的项才取旧键的值，两处都没写的取默认值。

端点与配置界面共用 `server.port`，不另占端口。

### 握手阶段的两道守卫

**一、只接受来自本机回环地址的连接。** 判据取自 TCP 对端地址，
**与 `server.address` 无关**——即使为了对外提供推送接口把监听地址改成 `0.0.0.0`，
事件流也只认本机。不通过时握手不进入 WebSocket 协议，客户端看到的是一个**空的 200**，
不是 401 也不是 403。

> ⚠️ 这道判据**不是**在开了 `server.forward-headers-strategy` 时仍然可信的来源判据：
> 那时 `X-Forwarded-For` 会改写它看到的地址。装了反向代理就必须打开 `require-token`，
> 那才是真正的门。

**二、握手里不许有凭据。** 带 `Authorization` 头、或带 `nova.token.` 开头的
`Sec-WebSocket-Protocol` 子协议，一律**拒收，回 HTTP 400**。

> `?token=` 这类查询参数**不是拒收，而是根本没人读**：它不会让你通过认证，
> 也不会得到任何提示。要认证只有 §4.2 那一条路。

理由是请求头会进反向代理的 access log，而各家代理遮蔽哪些头并不一致。
**拒收而不是忽略**：忽略等于留了一条看起来还能用的旧通道，口令照旧落进代理日志，
而客户端因为随后发了认证帧所以一切正常，没有任何人会发现。

## 2. 信封

### 三类消息，字段要求不同

**解析时必须先按 `kind` 分派再取字段，不能假设 `user` 一定存在。**

| 类别 | kind | 必带 | 不带 |
|---|---|---|---|
| 控制类 | `hello` `ping` `pong` `resume` `auth` `auth_failed` | `v` `kind` | `seq` `ts` `room` `user` |
| 房间级 | `live_state` `source_state` `room_stat` | `v` `seq` `ts` `kind` `room` `data` | `user` |
| 用户级 | `danmaku` `superchat` `gift` `guard` `enter` `follow` `share` `like` | 全字段 | — |

### 信封各键

| 键 | 类型 | 出现在 | 含义 |
|---|---|---|---|
| `v` | number | 全部 | 协议版本，**恒为 `2`** |
| `kind` | string | 全部 | 消息类型 |
| `seq` | number | 房间级、用户级 | 会话内序号，见下 |
| `ts` | number | 房间级、用户级 | 事件发生时间，**毫秒**，源侧时钟 |
| `room` | number | 房间级、用户级 | 房间号；取不到时为 `0` |
| `user` | object | 用户级 | 见 §5.1 |
| `data` | object | 除 `ping`／`pong` 外全部 | 按 `kind` 不同，见 §5、§6 |
| `rawJson` | string \| null | 房间级、用户级 | 平台原始报文的 JSON **文本**（不是对象）。**协议之外的附加字段，不是契约** |
| `reason` | string | 仅 `auth_failed` | 见 §4.3 |

`rawJson` 的字段随平台改版而变，脱敏时整段丢弃。由数据源自己合成的消息（如 `room_stat`）该键为 `null`。

**键的出现顺序不是契约**，按名取值，不要按位置。

### seq 的语义

从 **1** 开始严格递增，**只有房间级与用户级消息占号**，控制类消息不占。
会话内不重号、不缺号，因此下游可以拿它做去重与断线回补的唯一依据。

进程重启后 `seq` 从头开始，同时 `sessionId` 换成一个新值。
**客户端必须用 `sessionId` 判断是不是同一条流**：只看 `seq` 会把「重启后的第 5 条」
当成「重启前那条 5 的重复」而丢掉。

### 空值键必须存在

协议里大量字段是「可以为 `null`」而不是「可以不存在」——
`face`、`medal`、`emoji`、`replyTo`、`combo`、`blindBox`、`companionDays`、`startTs`、`rawJson`
都属此列。**这些键在任何情况下都会出现在报文里**，值可能是 `null`。

唯一的例外是 `room_stat` 的三项，它们是**可选键**：取不到时整个键不放，
一个显式的 `null` 在按协议生成的校验器眼里是类型错误。

### 一条连接承载全部房间

`room` 在每条房间级与用户级消息上都是必填的，**因为一条事件流里可以同时有多个房间**。
默认配置是「配了的主播全都连」，所以这不是边缘情况——实测一条连接里同时出现过 5 个房间号。

- **客户端必须按 `room` 过滤**，只消费自己关心的房间。
- **`seq` 是整条连接共用的，不按房间分。** 过滤时只能丢消息、不能丢序号，
  否则下一条本房间的消息会被判成跳号，凭空报出一次不存在的断档。
  判断有没有真丢包，要看**整条连接**的 `seq` 连不连续。
- `hello` 里没有 `room` 字段：连接建立时服务端并不知道客户端要看谁。

不过滤的后果不止是别人的弹幕混进流里——**账本一类的「本场累计」会把别的主播的礼物一起加进去**，
主播看到一个错的数字，而且没有任何提示。

### 示例帧（用户级）

```jsonc
{
  "v": 2,
  "ts": 1785858004052,          // 事件发生时间，毫秒
  "room": 12345,
  "kind": "danmaku",
  "user": {
    "uid": "3546...",           // 十进制字符串；匿名源的弹幕与礼物恒为 "0"
    "idKind": "uid",
    "name": "...",
    "face": "https://...",      // 可为 null
    "guardLevel": 3,            // 0 无 / 1 总督 / 2 提督 / 3 舰长
    "isAdmin": false,
    "isAnchor": false,
    "medal": { "name": "...", "level": 21, "isLighted": true }   // 可为 null
  },
  "data": { /* 按 kind 不同，见 §5 */ },
  "rawJson": "{\"cmd\":\"DANMU_MSG\",...}",   // 非契约，可为 null
  "seq": 10432                  // 服务端统一编号后补上
}
```

## 3. 时限

| 名目 | 值 | 谁的判据 |
|---|---|---|
| 心跳间隔 | **15 秒** | 服务端发 `ping` 的周期 |
| 服务端侧存活判据 | **45 秒**（＝3 个心跳周期） | 客户端这么久没发过任何帧即被断开 |
| 客户端侧断线判据 | **40 秒** | 客户端约定：这么久没收到 `ping` 即视为断线 |
| 认证窗口 | **10 秒** | 要求口令时，连上后这么久没发 `auth` 即被断开 |
| 回补窗口 | **2 秒** | 收到 `hello` 后这么久内可以发 `resume` |
| `room_stat` 最快间隔 | **5 秒** | 服务端限流上限 |

服务端与客户端的两个断线判据**不是同一个数**，各挡各的：客户端那 40 秒防的是
「服务端不吭声了」，服务端那 45 秒防的是「断电、崩溃这类不发 FIN 的客户端一直挂在订阅列表里」。

## 4. 握手、认证与回补

### 4.1 不要求口令时（默认）

```
1. 连上
2. ← {"v":2,"kind":"hello", "data":{…}}
3. → {"kind":"resume","data":{"fromSeq":<n>}}   想回补就在收到 hello 后 2 秒内发
4. ← 实时事件
```

不发 `resume` 也可以：2 秒窗口一到，服务端自行转入实时流。
**窗口期内产生的消息不会丢**——转入实时流时是从握手那一刻的序号接着补的。

### 4.2 要求口令时

口令**只在连接建立之后的第一帧**出示：

```json
{"kind":"auth","token":"<口令>"}
```

`token` 是唯一必填项。带上 `v` 也可以，**服务端不校验它**——所以别拿它做版本协商。

```
1. 连上                                          服务端静默
2. → {"kind":"auth","token":"…"}                 10 秒内
3. ← {"v":2,"kind":"hello", …}                   认证成功后才发
4. → {"kind":"resume","data":{"fromSeq":<n>}}    想回补就在收到 hello 后 2 秒内
5. ← 实时事件
```

🔴 **认证成功之前服务端什么都不发，`hello` 也不发。** `hello` 里带着会话标识、能力集与
口径差异，那是关于这个部署的信息，认证之前不该给出去。**因此客户端必须先开口**——
等 `hello` 再发口令会在 10 秒后被断开。

认证通过后重复发 `auth` 会被忽略：已经认过的连接不该被第二帧改变状态。
未要求口令的部署收到 `auth` 也不报错，直接忽略——客户端不该为了两种部署写两套代码。

**未认证之前，除 `auth` 外的帧一律不理会**，尤其是 `resume`：它能问出「缓冲窗口从哪一条起」，
那也是关于这个部署的信息。

### 4.3 `auth_failed`

口令不对时，服务端**先同步把这一帧写出去再关连接**：

```json
{"v":2,"kind":"auth_failed","reason":"bad_token"}
```

`reason` 在信封上，不在 `data` 里。取三值：

| 值 | 含义 | 客户端应当 |
|---|---|---|
| `bad_token` | 从没被签发过，或压根没出示 | 提示查证来源 |
| `revoked` | 曾经有效，已被吊销 | 提示查证来源 |
| `expired` | 已过期 | 提示重取 |

> `expired` **当前永远不会出现**：口令首版不带有效期，到期靠控制台吊销。
> 它写在这里是因为契约有三值，日后真加了有效期必须回这一项而不是 `bad_token`——
> 「过期了」和「这把口令根本不存在」对用户是完全不同的两件事。

⚠️ **逾期没认证那一路不发 `auth_failed`**，因为没人出示过任何东西。三种断法要分开处理，见 §7。

### 4.4 `hello`

```jsonc
{
  "v": 2,
  "kind": "hello",
  "data": {
    "sessionId": "b3f1…",          // 本次进程的会话标识
    "source": "novabot",
    "capabilities": ["danmaku","superchat","gift","guard",
                     "enter","follow","share","like","room_stat"],
    "lastSeq": 10432,              // 已分配出去的最大序号，还没发过时为 0
    "bufferedFrom": 8433,          // 回补缓冲里最老的 seq
    "notes": ["…"]                 // 面向人读的口径差异声明
  }
}
```

| 键 | 类型 | 含义 |
|---|---|---|
| `sessionId` | string | 本次进程的会话标识。变了表示数据源重启过，手里的 `lastSeq` 毫无意义 |
| `source` | string | 数据源标识，本实现恒为 `novabot` |
| `capabilities` | string[] | 本源真的会推的 `kind`，见下 |
| `lastSeq` | number | 已分配出去的最大序号；尚未发过任何消息时为 `0` |
| `bufferedFrom` | number | 缓冲里最老的序号。**缓冲为空时为 `lastSeq + 1`**，含义是「从下一条起才有」 |
| `notes` | string[] | 源侧的口径差异声明，可为空数组 |

`lastSeq` 与 `bufferedFrom` **取自同一瞬间**，客户端可以直接拿它们算能不能回补。

#### `capabilities` 的语义

**缺某项时，展示层隐藏对应 UI，而不是显示一个永远为空的区域。**
一个写着「在线 0」的面板会让主播以为没人在看；正确做法是不显示这一位。

新增 `capability` 不算破坏性变更，客户端必须忽略不认识的项。

#### `notes` 的语义

`string[]`，**面向人读的自由文本，不是机器判据**——客户端不得解析它来改变行为，
那是 `capabilities` 的职责。能力集只能表达「有没有这一类事件」，表达不了
「这一类事件与协议描述的口径差在哪」；这种差异写进报文里，对着连接排查的人才看得见。

客户端应当把它显示出来或打进日志。缺失时按空数组处理。

**当前取值（六条，属实现现状而非契约）**：点赞未聚合；`live_state` 没有中途接入的快照；
`source_state` 的 `disconnected` 只在主播被移出数据源时下发；房管标志只有弹幕消息带；
`danmaku.emoji` 只在整条即一张表情图时非空；`rawJson` 不是契约。

### 4.5 `resume`：三种情形，客户端要能区分

```json
{"kind": "resume", "data": {"fromSeq": <本地已持有的最大序号>}}
```

⚠️ **`fromSeq` 是「客户端已持有的最大序号」，服务端补 `seq > fromSeq`。**
把它理解成「我想要的第一条」会让每次回补都不多不少丢掉一条——
而丢的正是断线瞬间那一条，日志里看不出任何异常。

**必须在收到 `hello` 后 2 秒的宽限窗内发出。** 窗口一到服务端就转入实时流。

| 情形 | 条件 | 服务端行为 | 客户端应当 |
|---|---|---|---|
| 正常回补 | 同一 `sessionId`，且 `fromSeq + 1 >= bufferedFrom` | 补发缺口，再转实时流 | 按 `seq` 丢掉重叠部分 |
| 超窗 | `fromSeq` 早于缓冲起点 | **重发 `hello`，不回补** | 采纳新的 `lastSeq`，记一次补不回来的断档 |
| 越界 | `fromSeq > lastSeq` | **重发 `hello`，不回补** | 同上。这不是「缺口太大」而是「根本不是同一条流」 |
| 迟到 | `resume` 在转入实时流之后才到 | **重发 `hello`，不回补** | 同上，且不要再发一次 `resume` |

缺的那一段凑不齐时**宁可让客户端重来，也不会把残缺的一段发过去**——
补了一半的累计看起来精确而实际少算，比明说「补不上」危险得多。

后三种服务端都是重发 `hello` 而不是报错：**它没有「失败」，只是没法从你要的地方开始。**
客户端据此自行重置，而不是等一个永远不会来的错误码。

⚠️ 客户端收到第二份 `hello` 后**不要再 resume 一次**，否则会来回打转。
判据是「本次连接是否已经发过 `resume`」，按连接记而不是按会话记。

`data` 缺失或 `fromSeq` 缺失的 `resume` 会被**静默忽略**，服务端不回任何东西。

**断档不能静默吞掉**：补不回来的那一段之后，所有累计都是少算的，
没有任何时点能让它重新变准。此时本场累计应当改为 `≥` 前缀并显示断档标记——
宁可显示不精确，也不要显示一个看起来精确而实际少算的数。

## 5. 用户级消息

### 5.1 `user`

用户级消息全都带这个对象。

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `uid` | string | 否 | 用户标识的十进制字符串。取不到时为 `"0"` |
| `idKind` | string | 否 | `uid` 或 `openid`。本实现恒为 `uid` |
| `name` | string | 否 | 昵称。取不到时为空串 |
| `face` | string | **可为 null** | 头像地址 |
| `guardLevel` | number | 否 | `0` 无 / `1` 总督 / `2` 提督 / `3` 舰长 |
| `isAdmin` | boolean | 否 | 房管标志，见下 |
| `isAnchor` | boolean | 否 | 发送者是不是本房间的主播本人 |
| `medal` | object | **可为 null** | 粉丝勋章，见下 |

`medal` 非空时：`name`（string）、`level`（number）、`isLighted`（boolean），三项都必带。

⚠️ **`isAdmin` 只有弹幕消息带得出。** 礼物、上舰、进房这些消息的平台报文里根本没有这一位，
所以那里的 `false` 含义是「这条消息没说」，而不是「此人确认不是房管」。
**下游不要拿它做权限判断**，更不要因为同一个人在礼物消息上是 `false`
就撤销他在弹幕上显示的房管标识。

`isAnchor` 拿发送者 `uid` 与房间主播 `uid` 相比，不依赖报文里的任何标志位。
匿名源的弹幕上恒为 `false`——那时谁都对不上主播 `uid`，这是「比不了」而非「不是」。

#### 匿名源：抹除是按 kind 来的

数据源可以不登录运行。这种源下平台会抹掉一部分身份信息，
而**抹除的粒度是消息类型，不是整条连接**：弹幕与礼物的 `uid` 恒为 `"0"`、昵称只留首字，
而点赞、关注、分享的用户信息完整，头像与粉丝勋章两种模式下都是真的。

三条容易搞错的：

1. **`uid: "0"` 是合法值，不是缺失。** 不要把它当成解析失败，也不要因此丢弃事件。
2. **它是「这条消息」的性质，不是「这路连接」的不变式。**
   不要拿它判断整路连接是不是匿名源——匿名连接上收到一条关注就带着真实 `uid`，
   照连接级判据会把整路误判成登录态。要判也只能按 `kind` 判。
3. **打码后的昵称原样透传，不要自造文案。** 首字是平台给的真实信息，扔掉它就少了一份线索。

### 5.2 `danmaku`

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `text` | string | 否 | 正文，**保留表情占位符**（如 `[大哭]`） |
| `emoji` | object | **可为 null** | 仅「整条弹幕就是一张表情图」时非空 |
| `inlineEmojis` | array | 否，**恒存在** | 正文里嵌的表情，按占位符去重；没有时是**空数组** |
| `replyTo` | object | **可为 null** | @ 回复的对象 |
| `msgId` | string | 否 | 源侧唯一 id。**本实现恒为空串**，见下 |

`emoji` 非空时：`url`（string）、`w`（number）、`h`（number）。取不到尺寸时为 `0`。

`inlineEmojis` 的每一项：`placeholder`（string）、`url`（string）、`w`、`h`、`count`（均为 number）。

`replyTo` 非空时：`uid`（string）、`name`（string）。

```jsonc
// danmaku.data
{ "text": "谢谢困了哥[大哭][大哭][大哭]",
  "emoji": null,
  "inlineEmojis": [
    { "placeholder": "[大哭]", "url": "https://…", "w": 20, "h": 20, "count": 3 }
  ],
  "replyTo": null,
  "msgId": "" }
```

#### 表情弹幕有两类，字段也是两个

平台侧的表情弹幕有两类，渲染路径完全不同，协议各给一个字段：

| | 形态 | 协议字段 |
|---|---|---|
| 纯表情 | 整条弹幕就是一张图，`text` 是表情名 | `emoji` |
| 内联表情 | 文字里嵌若干张小图，`text` 保留 `[大哭]` 这样的占位符 | `inlineEmojis` |

**三条硬约束，源侧校验器已锁死，下游可以依赖：**

- **`inlineEmojis` 的键恒存在。** 没有内联表情时是**空数组**，不是漏键、不是 `null`。
  纯表情弹幕同样是空数组。下游少一个 null 判断。
- **`emoji` 与 `inlineEmojis` 互斥**：`emoji` 非空时 `inlineEmojis` 必为空。
  两者同时非空是源侧的错误——**不要写「先看 emoji 再看 inlineEmojis」这种兜底去掩盖它**，
  兜底会让源侧的错误永远不被发现。
- **`count` 永远 ≥ 1，不会是 0。** 源侧取不到时记 1
  （既然占位符出现在正文里，它至少出现过一次）。

两条约定：

1. **`placeholder` 是键，不是位置。** 同一个表情在一条弹幕里可能重复出现，
   下游按占位符字符串在正文里做替换。**不给下标**——下标会在正文被截断时失效。
2. **`count` 由源侧给，下游不要自己数。** 平台自带这个次数，
   自己数正文是重复劳动，而且遇到占位符恰好与用户输入的普通方括号文本撞车时会数错。

> ⚠️ **`emoji != null` 不是「这条有表情」的判据。** 它只认纯表情。
> 要判断「这条有没有图」，用 `emoji != null || inlineEmojis.length > 0`。
> 单看 `emoji` 会漏掉内联表情那一半——**这正是协议从 v1 升到 v2 的原因**，见 §9。

> 📐 内联表情的原生尺寸远小于纯表情，实测样例是 20×20，而纯表情是 162×162。
> 按原生尺寸摆在头显一类的远距离显示上会小到看不清，展示层应当自行放大。

#### 弹幕去重

**`msgId` 在本实现里恒为空串**，空串表示源侧给不出，不是「id 恰好为空」——
平台的弹幕报文最外层没有这一项，只有醒目留言与状态类消息才携带。
协议要求这个键存在，故给空串而不是漏字段。

**去重键按优先级取：**

| 机制 | 何时用 | 可靠性 |
|---|---|---|
| `seq` | **首选**。回补重叠、重复投递都靠它 | 精确，源侧保证严格递增 |
| `id:<msgId>` | `msgId` 非空的 kind | 精确 |
| `sem:<uid>:<ts>:<text>` | 前两者都没有时的**最后手段** | 匿名源下会误合并 |

> ⚠️ **不要直接拿 `msgId` 当键。** 照「必填且唯一」的假设写，所有弹幕会因为共用空串键
> 被归并成同一条——**面板上只剩一句话，而且不会有任何报错**。
>
> 语义键为什么是这三个字段：同一个人在同一毫秒发出两条一模一样的文本，
> 在直播场景里就是重复投递而不是两次发言。少了 `ts` 会把「同一个人隔了十分钟
> 又说了一遍 666」误判成重复删掉。

匿名源下 `uid` 恒为 `"0"`，语义键退化成 `sem:0:<ts>:<text>`，**不再能区分用户**。
**协议不为此做任何补救**，而是把优先级说清楚：`seq` 已经完整覆盖了协议层的重复投递场景，
语义键只在「客户端不跟踪 seq」时才需要。给退化的键人为加一个计数器让它永不碰撞，
等于把「去重」悄悄变成「不去重」并把问题藏起来——**宁可它有一个说得清的缺陷，
也不要它有一个看不见的谎言。**

### 5.3 `superchat`

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `text` | string | 否 | 留言正文 |
| `rmb` | number | 否 | 实扣，见 §6 |
| `durationSec` | number | 否 | 展示时长，**秒**。取不到时为 `0` |
| `messageId` | number | 否 | 平台侧编号。取不到时为 `0` |
| `startTs` | number | 否 | 起始时刻，**毫秒**。取不到时为 `0` |
| `endTs` | number | 否 | 到期时刻，**毫秒**。取不到时为 `0` |

⚠️ **单位：`startTs` / `endTs` 是毫秒，`durationSec` 是秒。同一条报文里两种单位并存。**
平台原本给的是秒，源侧已换算成毫秒——**下游不要再乘一次 1000**。
写死在这里是因为「时间戳」三个字不说明粒度，而错了不会报错：
秒当毫秒用会把留言判成 1970 年的事件，毫秒当秒用会得到一个五万年后的到期时间。

`0` 的含义是「平台没给这一项」——这四项在真实报文里都远大于 0，所以 `0` 不可能是合法值。

| `giftName` | string | 否 | 礼物名。取不到时为空串 |
| `num` | number | 否 | 个数。取不到时为 `1` |

| `rmb` | number | 否 | 【实扣】见 §6 |
| `faceRmb` | number | 否 | 【面值】非盲盒时等于 `rmb` |
| `icon` | string | **可为 null** | 礼物图标地址 |

### 5.5 `guard`

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `level` | number | 否 | `1` 总督 / `2` 提督 / `3` 舰长。**取值只有 1~3，不会是 0** |
| `levelName` | string | 否 | 与 `level` 对应的中文名 |
| `num` | number | 否 | 数量。取不到时为 `1` |
| `unit` | string | 否 | 单位，**原样透传** |
| `rmb` | number | 否 | 见下 |
| `companionDays` | number | **可为 null** | 陪伴天数。`null` 表示没解析出来，**不是 0** |

**`unit` 不一定是「月」，可能是「天」**（短期赠送）。文案必须用这个字段拼，不能写死。

⚠️ **`rmb` 不能拿去对账。** 平台的下单消息给的是挂牌价，实际成交价只有另一类消息才有，
而后者约有两成拿不到。协议层区分不了这两种来源。

⚠️ **`companionDays` 取不到时必须留空。** 它从播报文案解析而来，文案改版就会取不到。
**绝不要补一个 0**——「陪伴 0 天」会作为假信息出现在主播眼前。取不到时整段不渲染。

## 6. 金额口径

这是本协议最容易出错、也最容易造成实际伤害的部分。

> **整个显示层只认「观众消耗」（协议字段 `rmb`）。** 不是标价，不是面值。
> 金额显示错了会直接造成社交事故——主播按 ¥1 的热情感谢一个花了 ¥100 的人。

| 字段 | 含义 |
|---|---|
| `gift.rmb` | **实扣**。平台从观众账上扣掉的额度（元）。打折体现在它身上；盲盒取盲盒本身的价格 |
| `gift.faceRmb` | **面值**。礼物的名义价值（元）。非盲盒时等于 `rmb` |
| `superchat.rmb` / `guard.rmb` | 实扣 |

⚠️ **实扣不是「观众掏了多少真钱」。** 扣的是账上余额，而余额可能是白来的（活动、签到）
或以充值优惠价买来的。**那个数在直播间的数据里根本不存在**，所以协议与 UI 一律不叫它「实付」。

`gift.rmb` 是分级、置顶槽竞争、账本累计的**唯一基数**。

三条硬规则：

1. **用 `paid` 布尔值判定免费道具，不要用金额阈值。** 免费道具的价值字段可能是另一种货币的计数，
   按付费货币的比例换算会把一个免费小心心算成几毛钱。
2. **打折体现在 `rmb` 上。**
3. **盲盒按实扣（盲盒单价）分级**，不按爆出道具的面值。有人花 ¥100 开盲盒爆出一堆小心心，
   若按 ¥1 分级、主播随口带过，那是很伤人的。

## 7. 房间级消息

### 7.1 `live_state`

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `live` | boolean | 否 | 是否在播 |
| `title` | string | 否 | 直播间标题。未知时为空串 |
| `startTs` | number | **可为 null** | 开播时刻，毫秒。未在播或未知时为 `null` |

⚠️ **只在开播、下播、标题变更时下发，没有中途接入的快照。**
客户端接上时若还没收到过，说明源侧也还不知道。

`title` 取自源侧记住的最近一次房间信息——开播消息里没有标题，刚接上时只能给空串。
标题原样相同时不会重复下发。

### 7.2 `source_state`

| 键 | 类型 | 可空 | 含义 |
|---|---|---|---|
| `state` | string | 否 | `connected` / `reconnecting` / `disconnected` |

⚠️ **`disconnected` 只在主播被移出数据源时下发**，含义是「这个房间不会再有数据了」。
房间还在监听列表里时源侧会一直重连，那种情况一律是 `reconnecting`。

这条消息存在的理由：房间没了却收不到任何状态变化，面板上那一路就会**永远停在「已连接」**，
看着像还在采集，其实一条都不会再来。

### 7.3 `room_stat`

| 键 | 类型 | 必选性 | 含义 |
|---|---|---|---|
| `watched` | number | **可选键** | 累计「看过」人数 |
| `online` | number | **可选键** | 高能用户数 / 在线人数 |
| `likeTotal` | number | **可选键** | 本场点赞总数 |

约定：

- 三项都是**可选键**，源侧有哪个给哪个，**取不到的整个键不放**。
  显式的 `null` 是类型错误——这三项与协议其它「可空」字段的规矩相反，特此写明。
- **三项全空则不推送这条消息。**
- 源侧限流到**最快 5 秒一条**，且只在这三个数真的变过时才推——
  5 秒是上限不是节拍，一个没人看的房间不会每 5 秒发一条一模一样的数。
- 客户端：**不进历史流、不入库、不触发节拍、不触发重绘调度**，只保留最新一份用于顶栏。
- 顶栏优先显示 `watched`：直播间自己展示的就是这个数，主播的心理锚点与观众一致。

## 8. 心跳、错误与关闭

### 8.1 心跳

- 服务端每 **15 秒**发 `{"v":2,"kind":"ping"}`，客户端回 `{"kind":"pong"}`
- 客户端 **40 秒**未收到 `ping` 视为断线
- 服务端侧：客户端 **45 秒**没发过**任何**帧即被断开（`pong` 之外的任何帧同样刷新存活时间）
- 未认证的连接不参与心跳，它的清理由 10 秒那条更短的时限负责
- 重连建议指数退避：1 秒起，上限 30 秒
- 重连后若 `sessionId` 未变且缺口在缓冲范围内，走 `resume` 回补；否则清空本地状态

### 8.2 关闭码

服务端主动关闭时用的是标准 WebSocket 关闭码：

| 码 | 何时 | 客户端还会收到 |
|---|---|---|
| `1000` | 口令不对 | 先收 `auth_failed`，再正常关闭 |
| `1001` | 服务端关停 | — |
| `1008` | 逾期没认证，或超过 45 秒没回应心跳 | **没有 `auth_failed`**，只有带原因的关闭 |
| `1011` | 向这条连接写失败，或传输异常 | — |
| `1013` | 客户端消费过慢，待发队列满 | — |

`1013` 那一路是**有意断开而不是丢消息**：断开后客户端重新握手时能从 `hello` 看到缺口，
而丢消息是它永远不会知道的。待发队列的容量是**缓冲条数 + 256**，
留出的余量是为了让一次整窗口回补装得下，不至于刚补上就因为队列满被断开。

关停时服务端留 **200 毫秒**把已经排上队的关闭帧发出去再强杀——
写不动的那条连接本来就发不出去，等它没有意义。

### 8.3 不认识的东西一律忽略

服务端收到不认识的 `kind`、不是合法 JSON 的帧、缺 `fromSeq` 的 `resume`，
**都只记一行调试日志，不断连、不回错**。协议要求忽略而不是断连。

客户端同样必须忽略不认识的 `kind` 与字段。

## 9. 版本化

- **破坏性变更递增 `v`**，服务端在 `hello` 与每一条信封里声明
- **新增可选字段、新增 `kind`、新增 `capability` 不算破坏性变更**——客户端必须忽略
  不认识的 `kind` 与字段
- 每次变更在本文件顶部记录版本与日期，并同步改 `NovaEventEndpoint.PROTOCOL_VERSION`

### 版本不匹配时怎么办：不拒绝连接

> ⚠️ 拒绝连接意味着**主播一条弹幕都看不到**。降级永远好过黑屏。

| 情形 | 客户端应当 |
|---|---|
| 源侧版本**低于**客户端 | **照常连接、照常渲染**，同时在握手时**具名报错**（如「源侧协议 v1，需 v2」）并显著提示。缺失的能力按缺失渲染，不猜、不补默认值 |
| 源侧版本**高于**客户端 | 同样照常连接。协议要求客户端忽略不认识的字段与 `kind`，高版本源在这条纪律下是安全的 |

**判据放在握手，不放在逐条报文**：`hello` 里就能知道版本，比每条弹幕嗅探字段既早又准。
逐条的字段检查可以保留，但那是纵深防御——防的是「版本号对了而字段没跟上」这种更难查的情况。

**具名报错必须精确到「缺什么、要做什么」**，不能只说「版本不匹配」。

⚠️ **服务端不做版本协商**：它不读客户端发来的 `v`，也不会因为版本不同而改变行为。

### v2 破坏性变更的内容

`emoji` 的语义收严为「仅整条即一张表情图的弹幕」。

v1 的 `emoji` 对内联表情弹幕也非空（源侧取平台表情映射的第一项）。
既有消费者若用 `emoji != null` 判断「这条带表情」，**在 v2 下会漏掉内联表情那一半**——
这正是版本号存在的场景。同时新增 `inlineEmojis`（新增字段本身是兼容的，不构成升版理由）。

v1 那个折叠有两处静默的错：给出的对象里**没有占位符**，那张图连对应哪个占位符都答不出；
而「第一项」取的是平台那个 JSON 对象的迭代序，不是占位符在正文里的出现顺序。
下游看到的结果是「一段带若干字面占位符的文字 + 末尾一张来源不明的图」——
**渲染不会报错，只是渲染的东西是错的**。

**迁移**：把 `emoji != null` 改成 `emoji != null || inlineEmojis.length > 0`。

## 10. 自 v1 草案的变化

对照的是 v1 草案（消费方仓库里那份 `docs/protocol.md`）。**代码一字未改**——冻的就是在发的。

### 增

| 项 | 说明 |
|---|---|
| `auth` 帧 | 口令改在连接建立后的第一帧出示（`kind` + `token`），见 §4.2 |
| `auth_failed` 帧 | 信封上带 `reason`，取 `bad_token` / `revoked` / `expired` 三值 |
| 认证窗口 10 秒 | 逾期即断，且**不发** `auth_failed` |
| 认证前静默 | 要求口令时，认证成功前服务端什么都不发，`hello` 也不发 |
| 握手拒收凭据 | `Authorization` 头与 `nova.token.` 子协议一律回 HTTP 400 |

### 未变

三类消息与字段必选性；`seq` 语义（从 1、严格递增、只有房间级与用户级占号、
进程重启重置并换 `sessionId`）；一条连接承载多个房间与客户端的过滤义务；
`resume` 的宽限窗 2 秒及正常回补 / 超窗 / 迟到三种情形的处理；`hello` 的字段集；
`capabilities` 缺项即隐藏 UI；`notes` 是面向人读的自由文本；心跳 15 秒与客户端侧 40 秒；
重连指数退避 1 秒起、上限 30 秒；金额三条硬规则与「只认实扣」；
`emoji` 与 `inlineEmojis` 互斥、`inlineEmojis` 键恒存在、`count` ≥ 1；
`placeholder` 是键不是位置、`count` 由源侧给；`room_stat` 最快 5 秒一条、全空不推送、
顶栏优先 `watched`；匿名源按 `kind` 抹除且 `uid: "0"` 是合法值；
版本化规则（破坏性变更递增 `v`，新增可选字段 / `kind` / `capability` 不算破坏性）；
版本不匹配时不拒绝连接。
